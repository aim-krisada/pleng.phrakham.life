## A.2 `expandRepeats` เพดาน 2 รอบ — แก้เล็กหรือรื้อโครง → **แก้เล็ก (กลไก) + เพิ่มฟิลด์ (ข้อมูล)**

โค้ดจริง midi.js:96 — `if (bar.repeatEnd && pass < 2)`

- **กลไกวนไม่ต้องรื้อ** — เปลี่ยน `2` เป็นค่าที่อ่านจากข้อมูล จบ · prototype ทำ 3 รอบได้ทันที
  (`['B','C','B','C','B','C']`)
- **ที่ขาดคือ *ข้อมูล*** — โมเดลวันนี้ไม่มีที่เก็บ "ซ้ำกี่รอบ" เลย ต้องเพิ่ม `times` บน `repeat-end`
- **volta ต้องรับหลายเลข** — วันนี้ `{num}` ตัวเดียว · "รอบ 3 จบเหมือนรอบ 2" ต้องเป็น `[2,3]`
  (prototype ทำได้: `['B','D','B','E']`)
- 🔴 **สิ่งที่รื้อโครงจริงคือ repeat ซ้อน repeat** — `repStart` เป็นตัวแปรเดี่ยว ไม่ใช่ stack
  พิสูจน์แล้วว่า outer repeat หายไป (ได้ `A B B C` แทน `A B B C A B B C`)
  → ถ้าไม่ทำ nested = แก้เล็ก · ถ้าจะทำ = ต้องเปลี่ยนเป็น stack

**คำตอบ: แก้เล็ก** ตราบใดที่ไม่รับ repeat ซ้อน (ซึ่งคลังจริงมี `‖: :‖` แค่ 3 คู่ — ยังไม่มีของซ้อนแน่นอน)

# SPIKE B — เบราว์เซอร์บอก "ตำแหน่งจริงบนแป้น" ได้ไหม

## B.2 🔴 ข้อชี้ขาด: คืน "ชั้น Shift" ไหม → **ไม่คืน · ฟีเจอร์นี้พลาดเป้าทั้งอันถ้าพึ่ง API นี้อย่างเดียว**

ทดสอบตรงๆ: หาอักขระเป้าหมายทั้ง 8 ตัวใน layout map → **null ทุกตัว**
```
^ -> null    _ -> null    ~ -> null    ( -> null
) -> null    { -> null    } -> null    # -> null
' -> Quote   , -> Comma   . -> Period  - -> Minus   (ตัวที่ไม่ต้อง Shift เจอครบ)
```

สเปกยืนยันตรงกับที่วัดได้ (WICG Keyboard Map §getLayoutMap):
> "Let key be the `key` value that would be generated by layout if the key identified by code
> was pressed with **no modifiers**."

**= API นี้คืนเฉพาะชั้นล่างของแป้น ตามนิยาม ไม่ใช่ข้อจำกัดของ implementation**
และอักขระที่พี่เปาหาไม่เจอ **ทุกตัวอยู่ชั้น Shift ทั้งหมด** → พึ่ง API นี้อย่างเดียว = ตอบโจทย์ไม่ได้เลย

## B.3 ทางสำรอง → **มี และพิสูจน์แล้วว่าได้จริง: เรียนจาก keydown ที่ผู้ใช้พิมพ์สำเร็จ**

ยิง keydown จริงผ่าน CDP แล้วอ่านสิ่งที่หน้าเว็บจับได้ (ค่าดิบ):
```json
"^": {"code":"Digit6","shift":true}    "_": {"code":"Minus","shift":true}
"~": {"code":"Backquote","shift":true} "(": {"code":"Digit9","shift":true}
"#": {"code":"Digit3","shift":true}    "'": {"code":"Quote","shift":false}
```

**แล้วประกอบกับ `getLayoutMap` เพื่อได้ป้ายที่ตรงกับที่พิมพ์อยู่บนปุ่มจริง:**
`learned['^'].code = 'Digit6'` → `map.get('Digit6') = '6'` → `shift=true` → **`"⇧ + 6"`**

ผลรันจริง (`spike/cdp-compose.mjs`) — ไม่มีตาราง US hardcode สักบรรทัด:
```json
"composedLabel": { "^": "⇧ + 6", "ู": "6" }
```

**ทำไมทางนี้ปลอดภัยกว่าโดยธรรมชาติ:** มันบันทึก**เฉพาะสิ่งที่เกิดขึ้นจริงบนเครื่องนั้น** —
ยังไม่เคยพิมพ์ = ยังไม่รู้ = ไม่แสดง (ตรงกับกฎ SA "ไม่ชัวร์ห้ามแสดง" โดยอัตโนมัติ ไม่ต้องเขียน logic กัน)
· ใช้ได้ทุกเบราว์เซอร์ (`KeyboardEvent.code`/`shiftKey` เป็นของพื้นฐาน)
· ป้ายจะ**ค่อยๆ โผล่**เมื่อผู้ใช้พิมพ์ตัวนั้นสำเร็จครั้งแรก แล้วจำไว้ (localStorage)

⚠️ **ข้อแลก:** อักขระที่ผู้ใช้**ยังไม่เคยพิมพ์ได้เลย** จะไม่มีป้าย — ซึ่งคือเคสของพี่เปาพอดี (`^`)
→ **ต้องมีทางเติมเต็ม** เสนอ 2 ทางที่พิสูจน์แล้วว่าเป็นไปได้:
1. **เรียนข้ามอักขระ** — พิมพ์ `6` ครั้งเดียว → รู้ว่า `Digit6` ให้ `6` → ประกอบ `⇧+6` ได้ทันที
   **ถ้ายืนยันได้ว่าเป็นแป้นละติน** (ดู B.4) · getLayoutMap ให้ชั้นล่างครบ 48 ปุ่มอยู่แล้ว
2. **โหมด "สอนให้หน่อย"** — ปุ่มบนจอกดแล้วขอให้ผู้ใช้ลองกดปุ่มที่คิดว่าใช่ 1 ครั้ง → ยืนยันด้วยของจริง

## B.4 แป้นไทย → **ไม่ได้วัดของจริง (ดู NOT PROVEN) — แต่ไม่เปลี่ยนคำตอบ**

เครื่องนี้ติดตั้ง **ทั้ง en-US (0409) และไทย (041E)** = สภาพเดียวกับพี่เปา
แต่ **ไม่ได้สลับเลย์เอาต์ระบบเพื่อวัด** เพราะจะไปรบกวนการพิมพ์ของ P'Aim ที่กำลังใช้เครื่องอยู่ (กฎกลาง §4)

ที่บอกได้แน่นอนจากที่วัดมา:
- getLayoutMap คืน**เลย์เอาต์ที่ active ตอนนั้น** · บนแป้นไทย Kedmanee ชั้นล่างของ `Digit1-7`
  เป็นอักษรไทย ไม่ใช่ `1-7` → **ทางที่ 1 (เรียนข้ามอักขระ) ต้องเช็กก่อนว่า `map.get('Digit1')==='1'`
  จริงไหม** ถ้าไม่ใช่ = ไม่ใช่แป้นละติน = ห้ามประกอบป้าย
- ทางสำรองหลัก (เรียนจาก keydown) **ไม่ขึ้นกับเลย์เอาต์โดยโครงสร้าง** — พิสูจน์บางส่วนแล้ว:
  ยิงปุ่มกายภาพเดียวกัน (`Digit6`) 2 ครั้งด้วยผลต่างกัน (`^` แบบ shift · `ู` แบบไม่ shift)
  → ระบบแยกเก็บถูกต้อง ไม่ปนกัน (`{"^":"⇧ + 6", "ู":"6"}`)
- บนแป้นไทย **พิมพ์ `^` ไม่ได้เลย** ต้องสลับเป็นอังกฤษก่อน → ป้ายที่เรียนมาตอนอยู่โหมดอังกฤษ
  ยังคงถูกต้อง เพราะผูกกับปุ่มกายภาพ ไม่ใช่โหมดภาษา
