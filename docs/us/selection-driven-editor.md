## 1 · ปัญหา — วัดสดใหม่บน live วันนี้ (ไม่ยกเลขจากเอกสาร)

รัน `docs/reports/editor-ux-baseline.md` (สคริปต์เดียวกัน) บน `https://pleng.phrakham.life/#/studio` เพลงเปล่า 1 ห้อง · **desktop 1280×800**:

| Metric | วัดสดวันนี้ | เอกสารฐาน | target |
|---|---|---|---|
| ปุ่ม/ช่องกดได้พร้อมกัน (M1) | **100** (79 ปุ่ม + 10 ช่องพิมพ์ + ลิงก์) | 100 | < 25 |
| ปุ่ม "ฟัง" (M3) | **5** | 5 | 1 |
| ปุ่มพรีวิว (M4) | **3** | 3 | 1 |
| ปุ่มลบ (M7) | **3** | 3 | ที่เดียว/scope |
| ปุ่ม edhead แถวเดียว (M8) | **15** | 15 | ≤ 7 |

**✅ เลขไม่เน่า — วัดสดตรงกับ SSOT เป๊ะ.** และการวัดสดได้ของแถม = **ป้ายจริงของปุ่มฟังทั้ง 5:**

```
ฟังท่อนนี้ · ฟังบรรทัดนี้ · ฟังห้องนี้ · ฟังทั้งเพลง · ฟังท่อน A
   ↑ท่อน      ↑บรรทัด       ↑ห้อง       ↑ทั้งเพลง    ↑ท่อนที่เลือก
```

**นี่คือหลักฐานต้นเหตุ (root cause) แบบชี้ตัวได้:** ฟัง 5 ปุ่ม = **ระดับ scope 5 ระดับ ต่างคนต่างวางปุ่มฟังของตัวเอง** · ลบ 3 = `ลบบรรทัด · ลบโน้ตนี้ · ลบห้องนี้` (scope 3 ระดับ) · พรีวิว 3 = `ตัวอย่างสด · ดูผลทั้งเพลง · ดูผลห้องนี้`.

> **สรุปต้นเหตุ:** editor **ไม่ได้ขาดระบบเลือก** — มันขาด **การซ่อน**. ทุกระดับ scope วาดชุดเครื่องมือเต็มของตัวเองค้างไว้ตลอด → 100 ปุ่ม. นี่ผิด **NN/g #8 (minimalist)** · **Miller's Law (~7±2)** · **Hick's Law** (ปุ่มยิ่งเยอะ ตัดสินใจยิ่งช้า) ตามที่ `ui-standards §2` อ้างไว้อยู่แล้ว.

**หมายเหตุ:** จอเปล่า = **ค่าต่ำสุด** (floor). เพลงจริงหลายท่อน/หลายห้อง จำนวนปุ่ม**คูณตามจำนวนห้อง/โน้ต** → ตัวเลขบานกว่านี้มาก. (mobile 375px = 95, ล้นแนวนอน 285px ในภาวะ headless — ต้องวัดซ้ำที่ 360/412 จริงตอน build)

## 2 · เทียบ pattern โลกจริง (เปิดของจริง ไม่เล่าจากความจำ)

เปิดเอกสาร/ของจริงมาแล้ว 6 ตัว. **แบ่งได้ 3 ตระกูล** — สำคัญคือ **ตัวไหน "เข้ากับ pleng"** (เลข+เนื้อ+คอร์ด บนช่องพิมพ์ **ไม่ใช่ staff 5 เส้น**):

### ก. แผงข้าง (persistent side panel) ที่ "เปลี่ยนเนื้อตามสิ่งที่เลือก"
| ตัว | พฤติกรรม (จากของจริง) | เข้ากับ pleng? |
|---|---|---|
| **MuseScore 4 Properties (F8)** | *"ไม่เลือกอะไร → โชว์ตัวเลือกทั้งสกอร์ · เลือกโน้ต → โชว์เฉพาะ property ของโน้ต"* | ✅ **โมเดลตรงกับ P'Aim ที่สุด** — "ไม่เลือก=จอสะอาด, เลือก=เครื่องมือโผล่" คือโมเดลนี้เป๊ะ |
| **Hookpad (Hooktheory)** | เครื่องมืออยู่ **ขวาของ staff** · *"เปลี่ยนเป็นคอนโทรลคอร์ด หรือ โน้ต ตามสิ่งที่เลือก"* | ✅ แนวคิดใช้ได้ · ⚠️ แต่ pleng จอแคบ (มือถือ) วางแผงขวาถาวรไม่ไหว |
| **Figma inspector** | เลือก object → แผงขวาโชว์ property ของ object นั้น | ✅ หลักการเดียวกัน (desktop) |

### ข. ป้ายลอยติดตัวสิ่งที่เลือก (floating contextual near the object)
| ตัว | พฤติกรรม | เข้ากับ pleng? |
|---|---|---|
| **Flat.io Note toolbar** | แตะโน้ต → แถบเครื่องมือของโน้ตโผล่ · แตะซ้ำ = เปลี่ยนความยาว/ลบ · มือถือ: เครื่องมืออยู่**ล่างจอ** | ✅ ใกล้ pleng — pleng มี `slot-tools` (◀▶) โผล่เหนือช่องโน้ตตอน focus อยู่แล้ว |
| **Songsterr tab editor** | *"คลิกโน้ต → เปิดเมนูแก้แบบ contextual · พิมพ์เลข 0–9 เปลี่ยนโน้ต · Backspace ลบ"* | ✅✅ **ใกล้ pleng สุดในเชิงโดเมน** — Songsterr เป็น tab (ตัวเลข+ช่อง ไม่ใช่ staff) และ**พิมพ์เลขแก้โน้ตเหมือน pleng เป๊ะ** |
| **iOS edit menu (Apple HIG)** | แตะค้าง/ดับเบิลแตะ → ป้ายลอย (Copy/Paste/Delete) · *"ถ้าไม่มีอะไรถูกเลือก เมนูต้องไม่โชว์ตัวเลือกที่ต้องมี selection"* | ✅ เป็น **มาตรฐาน Apple ที่หนุนแนวคิด P'Aim ตรง ๆ** |

### ค. แถบบนแปลงร่างตอนเลือก (Material 3 Contextual Action Bar)
| ตัว | พฤติกรรม | เข้ากับ pleng? |
|---|---|---|
| **Material 3 CAB** | เลือกของ → **top app bar แปลงเป็นแถบ action ของสิ่งที่เลือก** · เลิกเลือก → กลับเป็นแถบปกติ | ✅ **เข้ากับ edhead ของ pleng ที่สุด** — edhead เป็นแถบบนอยู่แล้ว → ให้มัน "แปลงร่าง" ตาม scope ที่เลือก |

### สรุปว่าตัวไหนเข้า/ไม่เข้า pleng

- ✅ **เข้า:** **Songsterr + Flat** (โดเมน tab/ตัวเลข-พิมพ์ ตรง pleng) · **MuseScore Properties + Apple HIG** (โมเดล "ไม่เลือก=สะอาด, เลือก=โผล่" + กติกาซ่อนปุ่มที่ต้อง selection) · **Material CAB** (แถบบนแปลงร่าง = ตรงกับ edhead)
- ❌ **ไม่เข้า:** **แผงข้างถาวรของ MuseScore/Hookpad/Figma แบบตายตัว** — มันกิน**พื้นที่กว้างถาวร** เหมาะจอ desktop กว้าง แต่พี่เปาใช้**มือถือ** (จอ 360–412px) → แผงขวาถาวรจะเบียดโน้ต. เอา**หลักการ**มา (เปลี่ยนเนื้อตามการเลือก) แต่**ไม่เอารูปแบบแผงข้างถาวร**.
- ⚠️ **ข้อควรระวังจาก Apple HIG:** *"อย่าใส่ทั้ง context menu และ edit menu ให้ของชิ้นเดียว จะสับสน"* → pleng ต้องเลือก **ทางเดียว** (แถบ contextual เดียว) ไม่ใช่ทั้งป้ายลอย + แถบบน + เมนูขวาคลิก ปนกัน.

> **บทสรุปมาตรฐาน:** แนวคิด P'Aim **ไม่ใช่ของแปลกใหม่ที่ต้องเสี่ยงทดลอง** — มันคือแพตเทิร์นที่ **โปรแกรมโน้ตระดับโลกทำเหมือนกันหมด** และมี **มาตรฐาน Apple/Material หนุนเป็นข้อ ๆ**. เราไม่ได้เดิมพัน เราเดินตามทางที่พิสูจน์แล้ว.

## 3 · Feasibility กับโค้ดจริง (เปิด `EditorMode.vue` อ่านเอง — 4,575 บรรทัด)

> ⚠️ ไฟล์มี null byte บรรทัด 1569 → อ่านผ่าน `tr -d '\000' < file` (ripgrep ตรง ๆ หยุดอ่านกลางไฟล์)

### 3.1 ⭐ ค้นพบสำคัญ — editor **มี "การเลือก" ครบ 5 ระดับอยู่แล้ว**

| ระดับ scope | ตัวแปรสถานะที่มีอยู่แล้ว | บรรทัด | วันนี้ทำอะไร |
|---|---|---|---|
| **โน้ต/พยางค์** | `focusedSlot` | 324 | โฟกัสช่อง → โชว์ `slot-tools` (◀▶) เหนือช่องนั้น |
| **คอร์ดบนโน้ต** | `editingChord {li,bi,si,p}` | 423 | จิ้มคอร์ด → เปิดตัวแก้คอร์ดตรงโน้ตนั้น |
| **ห้อง** | `barMenuOpen "li-bi"` | 1805 | จิ้มห้อง → เปิด popover เครื่องมือห้อง (ทีละห้อง) |
| **บรรทัด** | `activeLine` | 877 | บรรทัดที่แตะล่าสุด = เป้าของปุ่ม ▲▼/ฟัง/ลบ ใน edhead |
| **ท่อน** | `activeStanza` / `lensChoice` | 189/? | ท่อนที่เลือก → โชว์ `cshead` (แก้ชื่อ/ทำนอง/คีย์/ย้าย/ลบท่อน) |

**นี่คือหัวใจของ feasibility:** โครง "เลือกแล้วรู้ว่าเลือกอะไร" **มีครบแล้วทั้ง 5 ระดับ**. `slot-tools`, `barMenuOpen` popover, `cshead` (โผล่เฉพาะ `lensActive`) **เป็น selection-driven อยู่แล้วบางส่วน**.

### 3.2 แล้วทำไมยังมี 100 ปุ่ม?

เพราะ **"การเลือก" วันนี้แค่ "ชี้เป้า" ไม่ได้ "ซ่อน"**:
- `activeLine` เปลี่ยน**เป้า**ของปุ่ม ▲▼ — แต่ปุ่ม ▲▼/ฟังบรรทัด/ลบบรรทัด (กลุ่ม `ed-quick` 6 ปุ่ม) **โชว์ค้างตลอด** ไม่ว่าเลือกบรรทัดหรือไม่
- ปุ่ม `ฟังท่อนนี้/ฟังบรรทัดนี้/ฟังห้องนี้/ฟังทั้งเพลง` **วางค้างทุกปุ่มพร้อมกัน** ไม่ได้ยุบเป็น "ฟังสิ่งที่เลือก"
- ห้องทุกห้องมีปุ่ม `+`/เครื่องมือของตัวเอง · โน้ตทุกตัวมีเครื่องมือรอบตัว → **คูณตามจำนวน element**

> **แปลว่า:** งานนี้ **ไม่ต้องสร้างระบบเลือกใหม่** (มีแล้ว) · แค่เพิ่ม **(1) ตัวบอก "ตอนนี้เลือก scope อะไร"** ตัวเดียว (รวม 5 ตัวข้างบนให้รู้ว่าอันไหนคือ "ที่กำลังโฟกัส") + **(2) เงื่อนไขซ่อน/โชว์กลุ่มปุ่มตาม scope นั้น**.

### 3.3 ของดีอีกอย่าง — action model เป็น **declarative อยู่แล้ว**

`editItems` (บรรทัด 1744) เป็น **array ของ object** ที่มี `place`, `anchor`, `row`, `hidden`, `pinnable`, `kind` — แถบเครื่องมือ render จาก data ไม่ใช่ปุ่ม hardcode กระจาย. **การเติม field `scope:` ให้แต่ละ item แล้วกรองตาม scope ที่เลือก = แก้ที่เดียว ครอบทุกปุ่ม** (ตรงหลัก `ui-standards §3` library กลาง). มี `hidden` เป็นเงื่อนไขซ่อนอยู่แล้ว → เพิ่มเงื่อนไข scope เข้าไปในกลไกเดิมได้.

### 3.4 สรุป feasibility

| | คำตอบ |
|---|---|
| ต้องรื้อสถาปัตยกรรมไหม | **ไม่** — state การเลือกครบแล้ว · action model เป็น data อยู่แล้ว |
| งานหลักคืออะไร | เพิ่ม `activeScope` 1 ตัว (รวม 5 selection ref) + field `scope` ต่อ item + `v-if` กลุ่มปุ่มตาม scope |
| จัดอยู่ในหมวด | **refine** (ต่อยอดของเดิม) — ตรง `feedback_refine_not_redesign` · **ไม่ใช่ redesign** |
| ~13 ปุ่มรอบโน้ต 1 ตัว | ยุบได้ (ดูเฟส 1) — เป้าเหลือ **แถบ contextual เดียว** ของ scope โน้ต แทนปุ่มลอยกระจาย |

## 4 · มือถือ (พี่เปาใช้จริง) — ข้อจริงที่ต้องแก้ให้ได้

พี่เปาแก้เพลงบนมือถือ 360–412px. ประเด็นมือถือที่ selection-driven **ต้องตอบให้ได้**:

1. **🔴 แป้นพิมพ์บังแถบล่าง (คอขวดจริง):** pleng แก้โน้ต/เนื้อ = **พิมพ์ในช่อง** → คีย์บอร์ดจอเด้งขึ้นกินครึ่งล่าง. ถ้าวางแถบ contextual **ล่างจอแบบ Flat** ตอนพิมพ์อยู่ → **คีย์บอร์ดบังแถบ**. → **ข้อเสนอ:** แถบ contextual ของ "โน้ต/พยางค์" ควรเกาะ**เหนือช่องที่เลือก** (แบบ `slot-tools` วันนี้ที่โผล่เหนือช่อง — พิสูจน์แล้วว่าไม่โดนคีย์บอร์ดบัง) ไม่ใช่ตรึงล่างจอ. ส่วนแถบของ scope ที่**ไม่ต้องพิมพ์** (ห้อง/บรรทัด/ท่อน = กดปุ่มล้วน) วางล่างจอแบบ CAB ได้.
2. **ไม่บังโน้ต:** ป้าย contextual ต้องเกาะติดสิ่งที่เลือกและ **clamp ไม่หลุดจอ** (`ui-standards §2` popup ห้าม scroll/หลุดขอบ) · จอง scroll ให้ช่องที่เลือกไม่โดนแถบทับ (`scroll-margin`).
3. **แป้นพิมพ์ชนการเลือก:** วันนี้ในช่องพยางค์ Space/Enter/Backspace/Delete ถูกจับเป็น "แยก/รวมพยางค์" แล้ว (`onSylKey` บรรทัด 371) → selection-driven ต้อง**ไม่ไปแย่ง** คีย์เหล่านี้ตอนโฟกัสอยู่ในช่อง (ใช้คีย์ลัดเฉพาะตอน "เลือก scope ที่ไม่ใช่ช่องพิมพ์").
4. **target size:** วัดสดวันนี้ under-44px = 56 ปุ่ม (desktop). ยุบปุ่มซ้ำ = **โอกาสทำให้ปุ่มที่เหลือใหญ่ขึ้นถึง 44px** (M9). ต้อง verify 360/412 จริง + `right ≤ viewport` ทุกปุ่ม (`feedback_verify_mobile_real_width`).
5. **regression guard:** ห้ามทำ M9(<44)/M10(<24)/M11(h-scroll=0) แย่ลง — วัดสดหลังทุกเฟส.

## 6 · ข้อเสนอ (ฟันธง 1 ทาง + ทำไมดีกว่าทางอื่น)

### 6.1 ทางที่แนะนำ — **"แถบเครื่องมือเดียวที่เปลี่ยนเนื้อตามสิ่งที่เลือก" (one contextual toolbar)**

รวมโมเดล 3 มาตรฐานที่เข้ากับ pleng:
- **ไม่เลือกอะไร → จอสะอาด:** โชว์เฉพาะ action ระดับ**เอกสาร** (ฟังทั้งเพลง · ดาวน์โหลด · บันทึกร่าง/เผยแพร่ · ย้อน/ทำซ้ำ · ตั้งค่า) — ตรง **MuseScore Properties** ("ไม่เลือก=ตัวเลือกทั้งสกอร์") + **Apple HIG** ("ไม่มี selection อย่าโชว์ปุ่มที่ต้อง selection")
- **เลือกโน้ต → เครื่องมือโน้ต** (จุดบน/ล่าง=ทบเสียง · เขบ็ต · เอื้อน · ลบโน้ต · คอร์ดที่โน้ต) เกาะเหนือช่อง (แบบ `slot-tools` เดิม แต่ครบเครื่อง)
- **เลือกห้อง/บรรทัด/ท่อน → เครื่องมือของ scope นั้น** ในแถบเดียว (แบบ **Material CAB** — edhead แปลงร่างตาม scope)
- **ทุก verb ยุบเป็นปุ่มเดียวชี้ scope ที่เลือก:** `ฟังสิ่งที่เลือก` · `ลบสิ่งที่เลือก` · `ดูผล` (5→1, 3→1, 3→1)

### 6.2 ทำไมดีกว่าทางอื่น (ไม่ list เฉย ๆ — เทียบให้เห็น)

| ทางเลือก | ผล | ตัดสิน |
|---|---|---|
| **คงเดิม (โชว์ทุกปุ่มทุก scope)** | 100 ปุ่ม · ผิด Miller/Hick/NN#8 · พี่เปาบ่น "งง" ทั้งวัน | ❌ นี่คือปัญหา |
| **รื้อทำใหม่ทั้ง editor** | เสี่ยงสูง · พี่เปาเรียนใหม่หมด · 3 เดือนไม่มีของถึงมือ · ทิ้ง 5 selection ref ที่ดีอยู่แล้ว | ❌ ผิด `refine_not_redesign` + big-bang |
| **แผงข้างถาวรแบบ MuseScore/Figma** | กินพื้นที่กว้างถาวร · จอมือถือ 360px รับไม่ไหว | ❌ ไม่เข้า pleng (มือถือ) |
| **✅ contextual toolbar เดียว (ต่อยอดของเดิม)** | ใช้ 5 selection ref + declarative editItems ที่มีอยู่ · ยุบปุ่มซ้ำอัตโนมัติ · แก้ที่เดียว · เดินเป็นเฟสได้ | ✅ **เล็กสุดที่แตะครบทุก metric** |

# 10 · ทิศทาง UX — เครื่องมือ **"โผล่ยังไง"** (hover เดสก์ท็อป / tap มือถือ)

**ผู้เขียน:** ที่นั่ง UX/UI · 2026-07-17 · **ต่อยอด §1–9 ของ SA** (SA ตอบ *"ยุบปุ่มได้ไหม/ทำได้ไหม"* = ได้ · ส่วนนี้ตอบ *"แล้วเครื่องมือควรโผล่มายังไง ให้พี่เปารู้ว่ากำลังทำกับอะไร"*)
**โจทย์จาก P'Aim (ตรง):** *"ยุบปุ่มอย่างเดียวไม่พอ — ลบบรรทัด จะลบบรรทัดไหน? ต้องเห็นว่าเลือกบรรทัดไหน · จริง ๆ ควรเป็น hover toolbox แบบ Photoshop ให้ใช้ง่ายจริง"* · **ข้อจำกัดหัวใจ:** พี่เปาใช้**มือถือ** — **มือถือไม่มี hover**

---

## 10.0 · ข้อสรุป (อ่าน 30 วิ · ฟันธง 1 ทาง)

| คำถาม | คำตอบ |
|---|---|
| **แนวคิด P'Aim (เครื่องมือติดกับสิ่งที่เลือก) ถูกไหม** | ✅ **ถูก 100% — เป็นมาตรฐานโลก** |
| **ลอก "hover toolbox แบบ Photoshop" ตรง ๆ ไหม** | ❌ **ไม่ — และนี่คือจุดที่ต้องเสนอให้ดีกว่าโจทย์** (เหตุผลข้างล่าง) |
| **แล้วเอาแบบไหน** | ✅ **แบบ Canva / Apple callout: "toolbox เกาะติด element ที่เลือก" ไม่ใช่แถบลอยอิสระ** · **tap-to-select เป็นหลัก · hover เป็นแค่ตัวช่วยบนเดสก์ท็อป** |
| **pleng ทำได้ไหม** | ✅ **ทำได้ · ทำอยู่แล้วครึ่งทาง** — `focusedSlot → slot-tools` (◀▶ เกาะเหนือช่องที่ tap) คือแพตเทิร์นนี้เป๊ะ · แค่ยังมีแค่ scope เดียว |
| **หน้าตา 1 ประโยค** | *"แตะสิ่งไหน → แถบเครื่องมือเล็ก ๆ ของสิ่งนั้นโผล่ติดตรงนั้น + ตัวนั้นถูกไฮไลต์ · ไม่แตะอะไร = จอสะอาด"* |

### ⭐ ทำไม **ไม่ลอก Photoshop** (เสนอเชิงรุก · มีหลักฐาน ไม่ใช่ความเห็น)

P'Aim อ้าง Photoshop เพราะ *"ใช้ง่าย"* — เราเห็นด้วยกับ**เจตนา** แต่**รูปแบบ**ของ Photoshop แก้โจทย์มือถือไม่ได้:

1. **Photoshop Contextual Task Bar = แถบ "ลอยอิสระ" ที่ผู้ใช้ลากเอง — ไม่เกาะติด element** ([Adobe docs](https://helpx.adobe.com/photoshop/desktop/get-started/learn-the-basics/boost-workflows-with-the-contextual-task-bar.html): drag-by-handle · pin · reset position). บนจอ 360px ของพี่เปา แถบลอยกลางจอ = **บังโน้ต** หรือ **ชนแป้นพิมพ์**
2. **เอกสาร Adobe เป็น desktop-only — ไม่มี trigger สำหรับ touch เลย** (agent เปิดของจริงยืนยัน: ไม่มี tap/mobile path). Photoshop ออกแบบมาให้ **เมาส์บนจอกว้าง** → รับมรดกมาตรง ๆ = รับ**สมมติฐาน hover/desktop** ที่พี่เปาไม่มี
3. **หลักมาตรฐานฟันธง:** [NN/g — Mouse vs. Fingers](https://www.nngroup.com/articles/mouse-vs-fingers-input-device/): *"a finger only has finger-down / finger-up — **touch has no hover state at all**"* และ *"contextual menus... **are less natural on touchscreens**"* → **ออกแบบ touch กับ pointer คนละท่า ไม่ใช่ยกท่า hover มาแปะ**

> **ดังนั้นทางที่ถูก = เอา "เจตนา" ของ Photoshop (เครื่องมือมาหาคุณตรงที่ทำงาน) แต่ใช้ "รูปแบบ" ของ Canva/Apple (เกาะติด element + tap-to-select) ที่มี touch story จริง.**

## 10.1 · เทียบ pattern "เครื่องมือโผล่ยังไง" — เปิดของจริง (ไม่เล่าจากความจำ)

โฟกัสมิติเดียว: **trigger (hover vs tap) + ตำแหน่ง (เกาะ element vs ลอย/แผงข้าง/แถบล่าง)** — ตัวไหน map กับ pleng (element = โน้ต/ห้อง/บรรทัด/ท่อน)

| ตัว (เปิดจริง) | desktop trigger | mobile/touch trigger | ตำแหน่ง toolbox | เข้ากับ pleng? |
|---|---|---|---|---|
| **Canva** ([help](https://www.canva.com/help/moving-elements/)) | คลิก element | **tap element** (+ tap-and-hold = เมนูเพิ่ม) | *"floating toolbar **that appears above or below it**"* (เกาะ element) | ✅✅ **ตรงที่สุด — มี touch story ครบ + เกาะ element** |
| **Apple HIG — Edit menu** ([HIG](https://developer.apple.com/design/human-interface-guidelines/edit-menus)) | secondary-click | **touch-and-hold / double-tap** | *"**above or below** the selection"* + *"visual indicator that **points to** the targeted content"* · ขยับเลี่ยงบังได้ | ✅✅ **มาตรฐานหนุนตรง ๆ** — วางบน/ล่าง + ลูกศรชี้ + กันบัง |
| **Notion** ([help](https://www.notion.com/help/writing-and-editing-basics)) | **hover** → `+`/`⋮⋮` ใน gutter ซ้าย | ❌ ไม่มี hover → **แถบ dock เหนือคีย์บอร์ด** | gutter ซ้าย (นอกเนื้อหา) / แถบล่าง | 🟡 หลัก "อยู่นอกทางเนื้อหา" ดี · แต่ gutter ซ้ายเปลืองที่บนจอแคบ |
| **Figma / FigJam** ([help](https://help.figma.com/hc/en-us/articles/4502073572247-FigJam-for-iPad)) | **คลิก**เลือก (ไม่ใช่ hover) | tap เลือก → toolbar ของ object | เดสก์ท็อป = แผงขวาถาวร · touch = toolbar เกาะ object | 🟡 แผงขวาถาวรกินจอมือถือ (SA ตัดไปแล้ว §2) · เอาแต่ "คลิกเลือก = หลัก" |
| **Material 3 CAB** ([TopAppBar](https://github.com/material-components/material-components-android/blob/master/docs/components/TopAppBar.md)) | เลือก → แถบบนแปลงร่าง | เลือก → แถบบนแปลงร่าง | แถบบน (ตรึง ไม่เกาะ element) | ✅ ดีสำหรับ scope ที่ action เยอะ (ท่อน) เป็น **fallback** |
| **Adobe Photoshop CTB** | เลือก tool/selection | ❌ **ไม่มีเอกสาร touch** | **ลอยอิสระ ผู้ใช้ลากเอง** ไม่เกาะ element | ❌ **ไม่เอา** (เหตุผล §10.0) |

**สรุปว่าเอาอะไร:** **Canva + Apple callout = แกนหลัก** (เกาะ element · tap-to-select · วางบน/ล่าง + ลูกศร · กันบัง) · **Notion** ให้หลัก *"เครื่องมืออยู่นอกทางเนื้อหา"* · **Material CAB** เป็น fallback เฉพาะ scope ท่อน (action เยอะ) · **Photoshop ไม่เอา**

## 10.2 · โมเดลเดียวทั้ง editor (consistency — งานหลักของที่นั่งนี้)

**กฎเดียว ทุก scope ใช้เหมือนกัน** (นี่คือหัวใจ — วันนี้แต่ละ scope โผล่คนละท่า = ไม่ consistent):

> **แตะ element → toolbox ของ element นั้นโผล่เกาะตรงนั้น + element ถูกไฮไลต์ค้าง · แตะที่ว่าง/แตะ element อื่น → toolbox ย้ายตาม · ไม่แตะอะไร = โชว์แค่แถบระดับเอกสาร**

| ชั้น | desktop | มือถือ (พี่เปา) | เหมือนกันตรงไหน |
|---|---|---|---|
| **เลือก** | คลิก element (**hover = เห็นเงา toolbox จาง ๆ ให้รู้ว่ากดได้** — ตัวช่วย ไม่ใช่ตัวสั่งงาน) | **tap element** | **การกด = การเลือก** (path เดียวกัน · hover เป็น sugar เดสก์ท็อปเท่านั้น) |
| **เห็นว่าเลือกอะไร** | element มี **outline ไฮไลต์ค้าง** (ไม่ใช่แค่ focus ring จาง) | เหมือนกัน — **สำคัญกว่าบนมือถือ** (คีย์บอร์ดบังครึ่งจอ ยังต้องเห็นว่าแก้ตัวไหน) | ตอบ P'Aim: *"ต้องเห็นว่าเลือกบรรทัดไหน"* เป๊ะ |
| **เครื่องมือโผล่** | toolbox เกาะ**เหนือ** element (ล่างถ้าไม่มีที่) | เหมือนกัน | Canva/Apple: above-or-below + ลูกศรชี้ |

**hover บนเดสก์ท็อป = ตัวช่วยค้นพบเท่านั้น** (แบบ Notion gutter ที่โผล่ตอน hover) — **ไม่ใช่ trigger การทำงาน** เพราะถ้าผูกการทำงานกับ hover = มือถือใช้ไม่ได้ (NN/g). → **เดสก์ท็อปกับมือถือใช้โค้ด selection ก้อนเดียวกัน · hover แค่เพิ่ม affordance ให้เมาส์**

## 10.3 · element ไหนได้ toolbox + โผล่ตรงไหน (ไม่บังโน้ต/ไม่ชนคีย์บอร์ด)

map เข้ากับ 5 selection ref ที่ SA เจอว่ามีอยู่แล้ว (§3.1):

| element | สถานะเดิม (§3.1) | toolbox โผล่ตรงไหน | เหตุผลตำแหน่ง |
|---|---|---|---|
| **โน้ต/พยางค์** `focusedSlot` | ✅ slot-tools เกาะ**เหนือช่อง**อยู่แล้ว | **เหนือช่องเสมอ** (ไม่เอาล่าง) | scope นี้**พิมพ์** → คีย์บอร์ดเด้งกินล่าง → บนคือที่เดียวที่ปลอดภัย (**พิสูจน์แล้วในโค้ดวันนี้**) |
| **คอร์ดบนโน้ต** `editingChord` | ✅ เปิดตัวแก้ตรงโน้ต | เหนือโน้ตนั้น | เหมือนโน้ต |
| **ห้อง** `barMenuOpen` | ✅ popover ต่อห้อง | เหนือห้อง (clamp ไม่หลุดจอ) | ไม่พิมพ์ → บน/ล่างได้ · ยึดบนให้ consistent |
| **บรรทัด** `activeLine` | 🟡 วันนี้ปุ่ม ▲▼/ฟัง/ลบ **ค้างใน edhead** | **ย้ายมาเกาะบรรทัดที่เลือก** | ตอบ P'Aim: *"ลบบรรทัดไหน"* → ปุ่มลบอยู่**ที่บรรทัดนั้น** ไม่ใช่แถบรวมบนสุด |
| **ท่อน** `activeStanza` | 🟡 cshead (แถบหัวท่อน) | หัวท่อน (Material CAB ได้ถ้า action เยอะ) | action ระดับท่อนเยอะ → แถบเดียวแปลงร่างรับได้ |

**กฎตำแหน่ง(Apple HIG · วัด/ทำจริง ไม่เดา):** วางเหนือ element ก่อน → ไม่มีที่ค่อยพลิกลง → **ลูกศรชี้ element** → **clamp ไม่หลุดขอบจอ** (ตรง `ui-standards §2` popup ห้ามหลุด/scroll) → scope ที่พิมพ์ = **บนเท่านั้น** (กันคีย์บอร์ดบัง §4.1)

## 10.4 · Feasibility — คำถามส่ง SA (ผ่าน PM)

UX ตรวจโค้ดเบื้องต้นแล้ว (ยืนยัน §3 ของ SA): **ไม่มี hover-to-reveal ใน editor เลย** (0 `mouseenter`/`mouseover` · pointer ทั้งหมด = drag/resize) → **เติม hover = additive ล้วน ไม่กระทบ touch** · `focusedSlot`+`slot-tools` (`EditorMode.vue:2809/2820`) = anchored + focus-driven + keyboard-safe อยู่แล้ว. เหลือ 3 ข้อให้ SA ฟันธง feasibility:

1. **anchor + clamp ต่อ element:** ทำ toolbox เกาะ**บรรทัด/ท่อน** พร้อม clamp ไม่หลุดจอ แบบเดียวกับ `barMenuOpen` popover ที่ห้องทำอยู่แล้ว — reuse กลไก popover เดิมได้ไหม หรือมีข้อจำกัดที่ผูกเฉพาะห้อง
2. **ทำ scope อื่นให้ conditional:** ย้ายกลุ่ม `ed-quick`/`seg-tools` จาก "โชว์ค้าง" → "โผล่เมื่อ element นั้นถูกเลือก" (via field `scope` ใน `editItems` ที่ SA เสนอ §3.3) — กระทบ test/keyboard-flow เดิม (`onSylKey`) จุดไหน
3. **มือถือ tap-to-select:** วันนี้ tap ช่องพิมพ์ = focus (ได้ toolbox). tap **ห้อง/บรรทัด/ท่อน** (ไม่ใช่ช่องพิมพ์) → set active scope + โผล่ toolbox โดยไม่เผลอเด้งคีย์บอร์ด ต้องแตะอะไรเพิ่ม · long-press สำหรับ multi-select (Canva) = เฟสหลัง ไม่ใช่ตอนนี้

## 10.5 · เฟส (ต่อจาก §7 ของ SA · เพิ่มชั้น "การโผล่")

| เฟส | เพิ่มจาก §7 | พี่เปาได้อะไร | บล็อก |
|---|---|---|---|
| **A** (คู่ §7 เฟส 0) | ยุบ verb ซ้ำ **เข้าไปอยู่ใน toolbox ของ element ที่เลือก** (ไม่ใช่แค่ยุบ) + **ไฮไลต์ค้าง element ที่เลือก** | เห็นชัดว่า *"เลือกอันนี้ → นี่คือเครื่องมือของอันนี้"* — ตอบ *"ลบบรรทัดไหน"* ทันที | 🟡 เลี่ยงชน dev เฟส1 (PM คิว) |
| **B** (คู่ §7 เฟส 1) | ไม่เลือก = จอสะอาด · แต่ละ scope โผล่ toolbox เกาะ element (โมเดล §10.2) · **+ hover peek เดสก์ท็อป** | จอ < 25 ปุ่ม · เครื่องมือมาหาที่ ๆ ทำงาน | 🔴 = "รื้อ dock" · รอเฟส1 merge + **P'Aim เคาะ** |
| **C** (คู่ §7 เฟส 2) | กฎตำแหน่ง anchor (บน=พิมพ์ · CAB=ท่อน) · target 48dp · **long-press multi-select** · verify 360/412 จริง | แก้บนมือถือลื่น ไม่โดนแป้นบัง ไม่บังโน้ต | 🔴 ต่อจาก B |

**target size (มาตรฐาน ไม่เดา):** ปุ่ม toolbox มือถือ = **48×48dp** ([Material](https://m3.material.io/foundations/designing/structure)) / **1cm** ([NN/g](https://www.nngroup.com/articles/touch-target-size/)) · ระยะห่าง ≥ 8dp · pointer 44dp — ยุบปุ่มซ้ำ (เฟส A) = ได้ที่ว่างทำปุ่มที่เหลือถึง 48dp (แก้ M9)

## 10.6 · หลักที่ต้องไม่พลาด (ยึด ui-standards + HIG)

- **ไม่เลือกอะไร = ห้ามโชว์ปุ่มที่ต้องมี selection** ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/edit-menus): *"if nothing is selected, avoid showing options that require a selection"*) · **ซ่อน ไม่ใช่ทำจาง** (Apple: *"Hide unavailable menu items, don't dim them"*)
- **1 element = 1 ทางเข้าเครื่องมือ** — เลือก contextual toolbar ทางเดียว (Apple: อย่าใส่ทั้ง context menu + edit menu ให้ของชิ้นเดียว) → ตรง `ui-standards §2` single-source-of-action
- **ไฮไลต์ที่เลือกต้องชัดค้าง** (ไม่ใช่ browser focus ring จาง) — Figma ใช้กล่อง**สีน้ำเงินค้าง** เป็นตัวชี้เลือก → pleng ใช้ **outline โทนแบรนด์ค้าง** · **บนมือถือคือชีวิต** (คีย์บอร์ดบังครึ่งจอ ยังต้องเห็นว่าแก้ตัวไหน)
- **regression guard เดิมทั้งหมด** (M9 <44 · M10 <24 · M11 h-scroll=0) วัดสด 360/412 ทุกเฟส

## 10.7 · ฟันธงขนาด (ตอบ SA 3 ขนาด) + mockup ให้ P'Aim ลองจริง

SA (`docs/reports/contextual-toolbox-feasibility.md`) ยืนยัน **โครงรองรับ · refine ไม่ redesign** และให้เลือก 3 ขนาด — **UX ฟันธง:**

| ขนาด (SA) | คือ | ตัดสิน + เหตุผล (อ้างมาตรฐาน) |
|---|---|---|
| **เล็ก** — คงแถวถาวร + เพิ่ม hover | เดิม + น้ำตาลเดสก์ท็อป | ❌ **ไม่พอ** — ไม่แก้ 100 ปุ่ม (§1) · hover ใช้บนมือถือไม่ได้ (NN/g touch ไม่มี hover) = ทิ้งพี่เปา |
| **กลาง** — toolbox เกาะ element ครบ 5 | Canva/Apple callout | ✅ **เอาอันนี้** — เล็กสุดที่แก้ครบ (ยุบซ้ำ + ตอบ "ลบบรรทัดไหน" + มือถือใช้ได้) · reuse `slot-tools`/clamp/state เดิม (SA Q1–Q3) |
| **ใหญ่** — panel เดียวลากได้แบบ Photoshop | `floatEl` เป็นฐาน | ❌ **ไม่เอา** — คือแถบลอยอิสระที่ §10.0 ค้านไว้: บนมือถือ 360px บังโน้ต/ชนคีย์บอร์ด (Adobe docs เอง desktop-only) |

> **ฟันธง: ขนาดกลาง — "toolbox เกาะติด element ครบ 5 ระดับ (tap นำ · hover เสริมเดสก์ท็อป)"** = world-class ที่สุด*สำหรับพี่เปาบนมือถือ* เพราะมันคือแพตเทิร์นเดียวที่มี touch story จริงและ pleng ทำครึ่งทางแล้ว

**สิ่งที่ต้องออกแบบจริง = 3 ช่องว่างที่ SA ชี้** (ไม่ใช่รื้อ): **(1) ตำแหน่ง/trigger consistent ทั้ง 5** (§10.2–10.3 = โดเมน UX) · **(2) ย้าย บรรทัด+ท่อน จากแถบถาวรมาลอยเกาะ element** · **(3) hover-preview เดสก์ท็อป** (`@media(hover:hover)` · tap=ความจริง hover=พรีวิว)

**เฟส (sync กับ SA §7.2):** **A** โน้ต+ห้อง + ไฮไลต์ (เสี่ยงต่ำ เริ่มได้) → **B** บรรทัด+ท่อน anchored (แตะ layout 2 scope = "รื้อกลาง" · **รอ P'Aim เคาะ GATE 1**) → **C** hover-preview + ขัดมือถือ (48dp · long-press · verify 360/412)
