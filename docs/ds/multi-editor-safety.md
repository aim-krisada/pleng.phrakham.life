### 1.1 ทางเขียนที่มีจริง — และเส้นที่รายงานเก่ายังไม่นับ

รายงาน 26 ก.ค. ไล่ไว้ **6 เส้นในแอป** ถูกต้องครบ (ยืนยันซ้ำที่ `origin/main`@`27978bf` + `origin/v1`@`9bb1c8d`)
ไม่มีเส้นไหนมีตัวกันเขียนทับเลย

**แต่มีเส้นที่ 7 ที่ยังไม่มีใครนับ และเป็นเส้นที่เขียนเพลงทีละหลายสิบเพลงจริง:**

เทมเพลตที่อยู่ในเรโปเองตอนนี้ (`docs/importing-songs.md:129-135`):

```sql
insert into public.songs (number, title_th, title_en, content)
values (NN, 'ชื่อเพลงไทย', null, $json$…$json$::jsonb)
on conflict (number) do update
  set title_th = excluded.title_th, title_en = excluded.title_en, content = excluded.content;
```

**= ทับทันที ไม่มียาม ไม่ถาม ไม่มี undo** ถ้าเลขเพลงนั้นมีเจ้าของอยู่แล้ว

ตรวจข้อมูลจริง 199 แถวแล้ว **เลขเพลงไม่ซ้ำกันเลยทั้งคลัง** (anuchon 1-120 · lem-yai 141-780 · ไม่มีเลขไหนใช้ข้ามเล่ม)
→ แปลว่า `on conflict (number)` **ยิงได้จริง** ไม่ใช่ทฤษฎี

*(มีอีกเทมเพลตหนึ่งที่ปลอดภัยกว่า — `tools/hymnal-samples/s032.sql` มียามที่ abort ถ้าช่องนั้นมีเพลง**ชื่ออื่น**อยู่
แต่ยามนั้นเทียบแค่ `title_th` → ถ้าชื่อเดิมแต่พี่เปาแก้เนื้อไปแล้ว มันจะ **UPDATE ทับเนื้อทั้งก้อนเงียบ ๆ**)*

**นี่คือข้อค้นพบที่ตัดสินทั้งดีไซน์:**
ตัวกันที่อยู่ในหน้าเว็บ (ล็อก · checkout · presence · ticket ฝั่ง client)
**ถูกข้ามทั้งหมดตั้งแต่วันแรก** โดยเส้นที่เขียนเพลงเยอะที่สุด → ยืนยันข้อบังคับ **D1**


## 3 · ชั้น 0 — ตัวกันจริง อยู่ในฐานข้อมูล (การันตี)

### 3.1 คอลัมน์ `version` (ไม่ใช้ `updated_at` เป็นตั๋ว)

```sql
alter table public.songs add column version bigint not null default 1;
-- trigger BEFORE UPDATE: new.version := old.version + 1
alter table public.song_drafts add column version bigint not null default 1;   -- แก้ F9
```

**ทำไมไม่ใช้ `updated_at` ที่มีอยู่แล้ว** (รายงาน 26 ก.ค. เสนอไว้):

- `updated_at` เป็น `timestamptz` ที่ PostgREST ส่งมาทศนิยม **4-6 ตำแหน่งไม่คงที่** (วัดจริง: 174 แถว 6 ตำแหน่ง · 24 แถว 5 · 1 แถว 4) และ JS `Date` เก็บได้ 3 → แปลงพลาดเมื่อไหร่ = **เซฟไม่ผ่านทั้งที่ทำงานอยู่คนเดียว** = ผิด **D2** ตรง ๆ
- `bigint` เทียบตรง ๆ ไม่มีเรื่อง format · ความหมายชัดว่า "นี่คือตั๋วกันชน" ไม่ใช่ "เวลาไว้โชว์"
- เรากำลังเขียน migration อยู่แล้ว (`deleted_at` + RLS + trash) → เพิ่มคอลัมน์นี้แทบไม่มีต้นทุนเพิ่ม และตัดบั๊กทั้งคลาสทิ้ง
- `default 1` = backfill ครบทันที ไม่ต้องย้ายข้อมูล

> **ยังต้องยืนยัน 1 ข้อก่อนลงมือ:** มี trigger ขยับ `updated_at` บน `songs` จริงไหม (Q9 ในไฟล์ SQL ของงานก่อน)
> F1 ชี้ว่ามีแน่ ๆ แต่ยังอ่าน `pg_trigger` ด้วยคีย์สาธารณะไม่ได้ · **ถ้าไม่มี ก็ใส่ในไฟล์ migration เดียวกันนี้เลย**

### 3.2 ถอนสิทธิ์เขียนตรง — แอปเขียน `songs` ตรง ๆ ไม่ได้อีกต่อไป

```sql
revoke insert, update, delete on public.songs from authenticated;
```

ทุกการเขียนต้องผ่าน RPC (`security definer`) ที่**บังคับตั๋ว**:

| RPC | ใช้ตอน | กันอะไร |
|---|---|---|
| `save_song(p_id, p_expected_version, p_patch)` | เซฟ/เผยแพร่จากหน้าแก้ (เส้น #1, #4) | ทับกันข้ามคน |
| `publish_from_draft(p_draft_id, p_song_id, p_expected_version, p_patch)` | อนุมัติ+เผยแพร่ (เส้น #6 · แทน `approve_and_publish`) | §7.2 |
| `restore_song_version(p_song_id, p_expected_version, p_revision_id)` | ปุ่ม ⏪ ย้อนเวอร์ชัน (เส้น #3) | §7.3 |
| `set_song_verified(p_id, p_expected_version, p_verified)` | ติ๊ก ✓ ตรวจแล้ว (เส้น #2) | เขียนคอลัมน์เดียว แต่ยังต้องมีตั๋วเพื่อไม่ให้ version หลุด sync |
| `trash_song` / `restore_from_trash` / `purge_song` | §6 | |
| `import_song(...)` | §5 — เส้น #7 | ทับตอน import |

**ทุกตัวจบใน statement เดียว** (`where id = … and version = p_expected_version`) แล้วเช็ก `not found`
→ ไม่มีช่อง read-then-write ให้แทรก:

```sql
update public.songs set … , version = version + 1
 where id = p_id and version = p_expected_version;
if not found then
  raise exception 'VERSION_MISMATCH' using errcode = 'P0001';
end if;
```

**ผลที่ได้ตรงกับ D1:** dev คนใหม่ที่ลืมใส่การเช็ก **เขียนไม่ผ่านเลย** ไม่ใช่ "เขียนผ่านแบบไม่ปลอดภัย"

**ข้อเสียที่ยอมรับ** (N ทัก · ตรวจแล้วเห็นด้วย): เสีย auto-generated write API ของ PostgREST ·
debug log เห็นชื่อ RPC แทน statement · dev ต้องผ่านฟังก์ชัน
→ ยอม เพราะ D1 คือโจทย์ที่ P'Aim สั่งมาตรง ๆ

**สิ่งที่ยังเขียนได้อยู่ และตั้งใจให้เขียนได้:** `service_role` + P'Aim ใน SQL Editor
(bypass RLS/grants ตามนิยาม) — คนถือ SQL console ทำอะไรก็ได้เสมอ นั่นถูกต้องแล้ว
**คำตอบของเส้นนั้นคือเทมเพลตที่ปลอดภัย (§5) ไม่ใช่ล็อก**

### 3.3 UX ตอนตั๋วไม่ตรง — ข้อนี้ห้ามพลาด (D2)

```
❌ ห้ามเด็ดขาด: "บันทึกไม่สำเร็จ" แล้วจบ / ปิดหน้าต่างทิ้ง / ล้างสิ่งที่พิมพ์
```

## 4 · ชั้น 1 — "ใครอยู่ตรงนี้" (ที่ไอเดีย checkout ของ P'Aim ไปอยู่)

### 4.1 ประเมินไอเดียของ P'Aim อย่างเป็นธรรม

> *"ทำระบบ checkout และ lock และปลด lock หลัง non-active … นาที และมี request lock
> แจ้งให้คนทำงานอยู่รู้ และอนุญาตหรือปฏิเสธ"*

**สิ่งที่ไอเดียนี้ถูก และถูกมาก:**
1. **เป็นคำตอบมาตรฐานจริงของวงการ** สำหรับเอกสารที่ **merge ไม่ได้** — Git LFS file locking ·
   SharePoint/Office check-out · ระบบ PDM/CAD ล้วนใช้แบบนี้ ไม่ใช่ไอเดียมือใหม่
2. **เพลง v2 คือเอกสารที่ merge ไม่ได้จริง ๆ** (`stanzas` + `arrangement` + อาร์เรย์รายพยางค์
   ซ้อนกัน — merge 3 ทางแล้วเพลงเพี้ยนเงียบ ๆ ซึ่งแย่กว่าทับแล้ว undo ได้)
3. **บอกก่อนเริ่มพิมพ์ ดีกว่าบอกตอนจบ** — optimistic lock ล้วน ๆ มีข้อเสียใหญ่ข้อนี้จริง
   (พิมพ์ไป 20 นาทีแล้วค่อยรู้ว่าชน) · ข้อนี้เราเก็บมาใช้ใน §4.4

**กับดักที่รู้กันในวงการ — และทำไมล็อกแข็งจึงไม่ใช่ตัวหลัก:**

| กับดัก | เกิดยังไง |
|---|---|
| ล็อกค้าง | ปิดแท็บ / เน็ตหลุด / ปิดฝาโน้ตบุ๊ก → ต้องมี heartbeat + TTV เสมอ (P'Aim คิดถึงข้อนี้แล้ว) |
| **ล็อกที่แย่งได้ = ไม่ใช่ล็อก** | ต้องมีทางปลดฉุกเฉิน (ไม่งั้นปิดแท็บทีมค้าง) → พอแย่งได้ **การันตีก็หายไป** แต่ทีมเชื่อว่าปลอดภัยแล้วจึงเลิกระวัง = อันตรายกว่าเดิม |
| คนถือไม่อยู่ | request/deny ต้องมีคนตอบ · เขากลับบ้านไปแล้ว = ทางตัน (ผิด **D3**) |
| **ล็อกมองไม่เห็นเส้นที่สำคัญที่สุด** | เส้น #7 (SQL import) ไม่มีวันเห็นล็อกในเบราว์เซอร์ · ปุ่ม ⏪ ย้อนเวอร์ชัน ก็ไม่เห็น |
| ล็อกกันตัวเองไม่ได้ | คีย์ด้วย user id → ไม่กันเคส 2 แท็บ (F9 = เคสที่เกิดจริงวันนี้) · คีย์ด้วย session → กันเจ้าตัวออกจากเพลงตัวเอง = น่ารำคาญ |
| เซฟสะดุด | ล็อกแข็งแปลว่าบางจังหวะ "เซฟไม่ได้" = ผิด **D2** ที่ P'Aim ตัดออกเอง |

**ฟันธง:** ล็อกแข็งจ่าย**ต้นทุนทั้งหมด**ของการล็อก แต่**ไม่ได้การันตี**กลับมาเลย
ส่วน optimistic ในชั้น 0 ให้การันตีจริงในราคาเกือบศูนย์
→ **เอา "ความรู้สึกแบบ checkout" ของ P'Aim ไว้ (§4.3) แต่ไม่เอา "การบล็อก"**
และเพราะชั้น 0 อยู่ข้างล่าง **การแย่งสิทธิ์จึงปลอดภัย** — แย่สุดคือเจอกล่องให้เลือก ไม่ใช่งานหาย

### 4.2 ตาราง `song_claims`

```sql
create table public.song_claims (
  song_id      uuid primary key references public.songs(id) on delete cascade,
  user_id      uuid not null,
  display_name text not null,          -- snapshot (แบบเดียวกับ db/004 actor_name)
  tab_id       text not null,          -- กันเคส 2 แท็บของคนเดียวกัน (F9)
  claimed_at   timestamptz not null default now(),
  heartbeat_at timestamptz not null default now()   -- ⚠️ server now() เท่านั้น
);
```

**⚠️ เวลาทั้งหมดต้องเป็น `now()` ของ Postgres — ห้ามรับ timestamp จาก client เด็ดขาด**
(G ทัก: นาฬิกาเครื่อง client เพี้ยน 3 นาที → claim หมดอายุทุก 30 วิ วนไม่จบ · ถูกต้อง รับมาแล้ว)
client ยิงแค่ `heartbeat(song_id, tab_id)` — DB เป็นคนประทับเวลา

### 4.3 จังหวะเวลา

| ค่า | ตั้งเท่าไหร่ | เหตุผล |
|---|---|---|
| heartbeat | **30 วิ** | มาตรฐาน presence ทั่วไป |
| "จาง" (ไม่ถือว่าอยู่แล้ว) | **90 วิ** = 3× heartbeat | เผื่อ network jitter (กฎ 3× heartbeat) |
| claim ปลดเอง | **15 นาที** ไม่ขยับ | สั้นกว่านี้ = ปลดตอนคนคิดงาน/รับโทรศัพท์ |
| คนถือไม่ตอบคำขอ | **2 นาที** → ปล่อยให้คนขอแก้ได้ | ผิด D3 ถ้าปล่อยให้รอไม่จบ |
| ปิดแท็บ | `sendBeacon` ปลดทันที (**best-effort**) | G ทักถูก: iOS Safari ทิ้ง beacon บ่อย → **ห้ามพึ่ง** · ตัวจริงคือ heartbeat หมดอายุ |

**⚠️ WCAG 2.2 SC 2.2.1 Timing Adjustable (Level A) — ข้อนี้บังคับ ไม่ใช่ nice-to-have**

ดึงตัวบทมาอ่านเองแล้ว: time limit ที่ระบบตั้ง ต้องเข้าเงื่อนไขอย่างน้อย 1 ข้อ ซึ่งข้อที่เราใช้ได้คือ **Extend** —
> *"ผู้ใช้ได้รับคำเตือนก่อนหมดเวลา และได้เวลาอย่างน้อย **20 วินาที** เพื่อขยายเวลาด้วยการกระทำง่าย ๆ
> และขยายได้อย่างน้อย **10 ครั้ง**"*

→ **claim 15 นาทีที่ปลดเองเงียบ ๆ = ตกมาตรฐาน**
→ **ต้องมี:** ที่นาทีที่ 14 ขึ้น toast **"ยังแก้เพลงนี้อยู่ไหม? [ยังอยู่]"** ค้างไว้ ≥ 20 วิ · ต่ออายุได้ไม่จำกัด
(ข้อนี้ N ทักมา · ผมไปเปิดตัวบท W3C อ่านเองแล้วยืนยันว่าถูก และเป็น Level A จริง)

### 4.4 จังหวะที่ผู้ใช้เจอ (สิ่งที่แก้ข้อเสียใหญ่ที่สุดของ optimistic lock)

**(ก) เปิดเพลงที่มีคนแก้อยู่** → เข้า **โหมดอ่านอย่างเดียว** + แบนเนอร์
`"พี่เปากำลังแก้เพลงนี้อยู่ (อัปเดตเมื่อ 20 วินาทีที่แล้ว)"` · ปุ่ม **[ขอสิทธิ์แก้]** **[ดูอย่างเดียว]**
→ ได้ "ความรู้สึก checkout" ตามที่ P'Aim ต้องการ: ต้อง**ตั้งใจกด**ถึงเข้าแก้ ไม่ได้หลุดเข้าไปพิมพ์ทับ

**(ข) ขอสิทธิ์** → คนถือเห็น toast `"มีคนขอแก้เพลงนี้ — [ให้] [ไม่ให้]"`
- **ไม่ตอบใน 2 นาที** → คนขอเห็น `"ไม่มีการตอบกลับ — แก้ต่อได้เลย ระบบกันงานทับกันให้อยู่แล้ว"` + ปุ่มเข้าแก้ (**D3**)
- **[ไม่ให้]** → `"ตอนนี้ยังแก้ไม่ได้ — ขอทำให้เสร็จก่อน"` + [เตือนฉันเมื่อว่าง] + [ดูอย่างเดียว]
  · **การปฏิเสธมีอายุ ไม่ถาวร** — พอ claim หมดอายุก็เข้าแก้ได้ (ไม่งั้น deny ที่ถูกลืม = ล็อกเพลงตลอดกาล)

**(ค) ⭐ มีคนเซฟระหว่างที่เราพิมพ์อยู่** → นี่คือจังหวะที่สำคัญที่สุด และเป็นคำตอบต่อข้อท้วงของ G (§7.6):
แถบเตือน **โผล่ทันทีตอนเขาเซฟ** (ไม่ใช่ตอนเรากดเซฟ):
`"พี่เปาเพิ่งบันทึกเพลงนี้ — [ดูว่าเขาแก้อะไร] [แก้ต่อของฉัน]"`
→ **ไม่มีทางที่จะพิมพ์ 20 นาทีแล้วค่อยรู้ว่าชน** ซึ่งเป็นข้อเสียเดียวที่แท้จริงของ optimistic lock

**(ง) กลับมาจากเครื่อง sleep** (G ทัก · รับมาแล้ว) → ที่ `visibilitychange`/focus ต้อง
**เช็ก claim + version ใหม่ก่อนเสมอ** · ถ้าเพลงขยับไปแล้ว บอกทันที **ก่อน**ที่เขาจะพิมพ์ต่อ
ไม่ใช่ปล่อยให้ไปเจอ VERSION_MISMATCH ตอนกดเซฟ

**(จ) คนเดียว 2 แท็บ** (F9 — เคสที่เกิดจริงวันนี้) → `tab_id` ต่างกัน แต่ `user_id` เดียวกัน
→ ข้อความเฉพาะ: `"คุณกำลังแก้เพลงนี้อยู่ในอีกแท็บหนึ่ง — [ไปที่แท็บนั้น] [แก้ที่นี่แทน]"`

## 5 · เส้น #7 — import ชุดใหญ่ (ตอบคำถามที่ค้างจากงานก่อน)

### 5.1 คำถาม: การอัปโหลดชุด "สร้างใหม่อย่างเดียว หรือทับเพลงเดิมได้"

> ### 🔴 คำตอบ: **ทับเพลงเดิมได้ และเทมเพลตหลักในเรโปทับแบบไม่มียามเลย**

หลักฐาน: `docs/importing-songs.md:129-135` = `on conflict (number) do update set title_th, title_en, content`
· ตรวจข้อมูลจริงแล้วเลขเพลงไม่ซ้ำทั้งคลัง → conflict target ยิงได้จริง (§1.1)

**แต่ตามที่ P'Aim สั่ง — ดีไซน์นี้ไม่ได้พึ่งคำตอบนี้เลย** ต่อให้ import จะสร้างใหม่อย่างเดียว
ชั้น 0 ก็ยังบังคับให้ทุกการเขียนมีตั๋วอยู่ดี ระบบกันตัวเองโดยไม่ต้องเชื่อใคร

### 5.2 สิ่งที่ต้องทำกับเส้นนี้

```sql
create function public.import_song(
  p_category text, p_number int, p_title_th text, p_content jsonb,
  p_expect   text default 'new'   -- 'new' = ต้องเป็นช่องว่างเท่านั้น
                                  -- 'update:<version>' = ตั้งใจทับ และรู้ว่าทับเวอร์ชันไหน
) returns uuid …
```

- `p_expect = 'new'` แล้วช่องนั้นมีเพลงอยู่ → **abort ทั้ง batch** พร้อมบอกว่าชนเพลงไหน
- ตั้งใจทับ → ต้องระบุ version ที่เห็น → ถ้ามีคนแก้ระหว่างนั้น abort
- ทุก batch ได้ `op_group` เดียว → หน้าประวัติแสดงเป็น "นำเข้า N เพลง" ก้อนเดียว **และย้อนได้ทั้งก้อน**
- **แทนที่เทมเพลตเดิมใน `docs/importing-songs.md` ทันที** — เทมเพลตนั้นเป็นระเบิดที่วางอยู่ในเรโป

## 6 · ชั้น 2 — เจ้าของ · สิทธิ์ · ลบ + ถังขยะ

### 6.1 เจ้าของ (ownership)

**ตัดสินใจ: ใช้ `author_id` ที่มีอยู่แล้วเป็น "ผู้ดูแลเพลง" — ไม่เพิ่มคอลัมน์ `created_by`**
(เหตุผลตามงานปรึกษา 26 ก.ค.: ในเรโปนี้ `author_id` = คนสร้างเรคคอร์ด ไม่ใช่ช่องผู้ประพันธ์เพลง — `db/006` เขียนไว้ชัด)

**`author_id IS NULL` (93 เพลง import) = เป็นของคลัง → approver เท่านั้นที่ทำสิ่งที่ทำลายได้**
⛔ **ห้ามยกให้ใครเป็นเจ้าของ** — ยก 120 เพลงให้คนเดียว = วันหนึ่งคนนั้นลบได้หมดทั้งล็อต

### 6.2 ตารางสิทธิ์

| การกระทำ | anon | editor | approver | เจ้าของเพลง |
|---|---|---|---|---|
| เปิด/แก้/พิมพ์/โหลด JSON | ✅ | ✅ | ✅ | ✅ |
| บันทึกร่าง / ส่งตรวจ | ❌ | ✅ | ✅ | ✅ |
| เผยแพร่ (เขียน `songs`) | ❌ | ❌ | ✅ | ❌ |
| **ย้ายลงถังขยะ** | ❌ | เฉพาะเพลงตัวเอง | ✅ ทุกเพลง | ✅ |
| **กู้จากถังขยะ** | ❌ | เฉพาะของตัวเอง | ✅ ทุกเพลง | ✅ |
| **ลบออกจากคลังถาวร / เทถัง** | ❌ | ❌ **ไม่มีวัน** | ✅ | ❌ |
| แย่ง claim | ❌ | ✅ (มีการแจ้ง) | ✅ | ✅ |

**ตัดสินใจ: คง 2 role ไว้ ไม่เพิ่ม role ที่ 3**
N เสนอ role "Curator" โดยให้เหตุผลว่า *"editor ใหม่จะแก้เพลงที่ author_id เป็น NULL ไม่ได้"*
— **ตรวจที่ source แล้วเหตุผลนี้ผิด**: editor แก้ผ่าน `song_drafts` ซึ่งเป็นคนละตารางและมี RLS ของตัวเอง
(`db/002:58-65` — insert/update ร่างของตัวเองได้ ไม่เกี่ยวกับว่าใครเป็นเจ้าของเพลง)
→ **editor ทุกคนแก้ได้ทุกเพลงอยู่แล้ว** ownership กั้นเฉพาะการกระทำที่ทำลาย
2 role + ownership เป็นแกนตั้งฉาก = พอ · ทีม < 5 คน การเพิ่ม role = ภาระดูแลเปล่า ๆ

> **เงื่อนไขที่จะกลับมาทบทวน:** วันที่ต้องการคนที่ *เผยแพร่ได้ แต่ห้ามลบเพลงคนอื่น* → ค่อยเพิ่ม role ที่ 3

### 6.3 ลบ + ถังขยะ (ยืนตามงานปรึกษา C+G+N 26 ก.ค.)

```sql
alter table public.songs add column deleted_at timestamptz default null;
create index songs_trash_idx on public.songs (deleted_at) where deleted_at is not null;
```

- **public read RLS ต้องเปลี่ยนเป็น** `verified = true AND deleted_at IS NULL` (แก้ `db/005`)
- **ถังขยะ = route แยก `/trash`** เข้าจาก nav หลัก (ไม่ใช่ filter ปนในลิสต์) — ตาม Google Drive / M3 Navigation
- การ์ดในถังโชว์ **"เหลือ N วัน"** (iOS Photos "Recently Deleted")
- editor เห็นถังของตัวเอง · approver เห็นทั้งหมด
- **auto-purge = pg_cron รายวัน** (⛔ ไม่เอา purge-on-read)
- client `.select()` ต้องเพิ่ม `author_id, deleted_at, version` (`SongList` `Studio` `SongViewer` — วันนี้ยังไม่ได้ดึงเลย · F4)

**ลบ → Undo toast · ลบถาวร → modal** (M3: dialog เป็นการขัดจังหวะ ใช้ให้น้อย · HIG: เตือนก่อนทำลายข้อมูลถาวร)

> **แต่ toast ไม่ใช่ทางกู้คืนจริง** — Snackbar หายเองใน ~2-3.5 วิ (ค่ามาตรฐาน Material) ซึ่งสั้นเกินกว่าจะพึ่งได้
> และ toast ที่หายเองก็เป็น time limit ตาม SC 2.2.1 อีกเหมือนกัน
> → **ทางกู้คืนที่แท้จริงคือหน้า `/trash` ที่อยู่ 30 วัน** · toast เป็นแค่ทางลัด
> (นี่คือวิธีที่ Gmail/Drive ทำจริง และทำให้เราไม่ต้องไปสู้กับเรื่อง timing accessibility เลย)
