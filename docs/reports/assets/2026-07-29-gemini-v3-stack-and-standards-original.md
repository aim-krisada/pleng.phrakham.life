### 1. เรื่องการจัดการเวอร์ชันเมื่อเพลงผิด: "ค้าง Public เก่าไว้" vs "ถอดออกทันที (Unpublish)"

**คำตอบสั้นๆ:** **ควรแยก "ชนิดของข้อผิดพลาด" ก่อนครับ** แต่ถ้าเอา **เรียบง่ายและลดความสับสนที่สุด** ฝั่งผู้แต่งเพลงควรใช้โมเดล **Draft & Published** ครับ

#### ทำไมทางเลือกไหนถึงเหมาะ?
* **ถ้าผิดเรื่องข้อมูล/เนื้อหาเล็กน้อย (เช่น พิมพ์คำผิด, ใส่คอร์ดผิด):** 
  การค้างเวอร์ชันเก่าไว้ แล้วส่ง **"เวอร์ชันใหม่ (Draft/Revision)"** เข้าไปตรวจ โดยที่เวอร์ชัน Public ยังทำงานอยู่ ถือเป็น **Standard Practice ของ CMS ทั่วโลก** (เหมือน WordPress, Medium หรือระบบบทความ) เพราะคนฟังทั่วไปจะได้ไม่เสียประสบการณ์การใช้งาน เพลงไม่หายไปจากเพลย์ลิสต์
* **ถ้าผิดร้ายแรง (เช่น ผิดลิขสิทธิ์, เนื้อหาไม่เหมาะสม):** 
  ผู้อนุมัติ (Admin/Approver) ต้องมีปุ่ม **"Take Down" หรือ "Unpublish"** เพื่อปลดออกจากหน้า Public ทันที ไม่ว่ากำลังส่งตรวจใหม่หรือไม่ก็ตาม

#### ข้อเสนอแนะการออกแบบ Workflow สถานะ (Status Lifecycle)
เพื่อแก้ปัญหาDev อยากเก็บเวอร์ชัน แต่คุณไม่อยากให้คนสับสน ให้ใช้สถานะ 4 ตัวนี้ครับ:

1. **Draft (กำลังแก้ไข):** อยู่ในเครื่องผู้แต่ง/ระบบส่วนตัว (ยังไม่ส่งตรวจ)
2. **Pending Approval (รอตรวจ):** ส่งให้ผู้อนุมัติแล้ว
3. **Published (เผยแพร่แล้ว):** อยู่ในคลังเพลง คนฟังทั่วไปเห็น
4. **Unpublished / Archived (ยกเลิกการเผยแพร่):** ถูกปลดออกจากคลังเพลง (อาจเพราะผิดร้ายแรง หรือผู้แต่งถอดออกเอง)

> **สรุปคำแนะนำ:** ไม่จำเป็นต้องเลือกอย่างใดอย่างหนึ่งครับ **ให้คง Public ไว้ตามที่ Dev บอกเป็นค่าเริ่มต้น** เพื่อไม่ให้เพลงขาดช่วง (Live Update) **แต่เพิ่มปุ่ม "Unpublish / ถอดออกจาก Public" ให้ผู้อนุมัติ** เผื่อกรณีเพลงนั้น "ผิดร้ายแรงจนค้างไว้ไม่ได้" ครับ

เป็น 3 คำถามที่เจาะลึกและสะท้อนให้เห็นว่าคุณกำลังมองในมุมของการนำไปพัฒนาจริง (Implementation) และการทำงานเป็นทีมได้ดีมากๆ ครับ ผมขอตอบและเสนอทางออกทางเทคนิคให้ทีละข้อนะครับ เพื่อให้คุณนำไปคุยกับ Dev และพี่เปาได้เลย

### 1. เรื่อง Data Entity: ต้องแยก 2 Entity หรือทำ Version Control?

ทางเทคนิคทำได้ 2 แบบครับ แต่ผมขอแนะนำ **แบบที่ 2 (Version Control แบบย่อ)** เพราะจะตอบโจทย์ระยะยาวและสอดคล้องกับความต้องการของพี่เปาด้วยครับ

*   **แบบที่ 1: แยก 2 Entity (ตารางเพลง Draft กับ ตารางเพลง Publish)**
    *   **การทำงาน:** มีฐานข้อมูล 2 ก้อน พอแก้ไขก็ก๊อปปี้จาก Publish มาใส่ Draft ตรวจเสร็จก็เอาไปทับ Publish
    *   **ข้อดี:** Dev ทำงานง่ายและเร็วที่สุดในตอนแรก
    *   **ข้อเสีย:** ตามประวัติไม่ได้เลย และการเปรียบเทียบเวอร์ชันจะทำได้ยาก
*   **แบบที่ 2: Entity เดียว แต่ใช้ระบบโครงสร้าง Version (แนะนำแบบนี้ครับ 🌟)**
    *   **การทำงาน:** มี Entity หลักคือ "ข้อมูลทั่วไปของเพลง" (เช่น ชื่อเพลง) และมี Entity ลูกคือ "เวอร์ชันของเนื้อเพลง/โน้ต"
    *   *ตัวอย่างฐานข้อมูล:* เพลง "ความรักยิ่งใหญ่" (Song ID: 001) มี Version 1 (Status: Published) และ Version 2 (Status: Pending)
    *   **สรุป:** ให้ Dev ออกแบบเป็น Entity เดียวแต่มี Table เก็บประวัติ Version ครับ ซึ่งระบบจัดการ Content (CMS) ส่วนใหญ่ใช้ท่านี้ครับ

### 2. ฟีเจอร์ของพี่เปา: "เปรียบเทียบเวอร์ชัน" และ "แชทคุยกัน" (ทำได้ไหม? งานช้างหรือเปล่า?)

คุณกังวลถูกแล้วครับ! ถ้าทำแบบจัดเต็ม มันคือ **"งานช้าง"** สำหรับ Dev แน่นอนครับ โดยเฉพาะ MVP (เวอร์ชันแรก) ผมขอเสนอ **"ทางเลือกลดสเกลงาน (Trade-off)"** ที่ได้ผลลัพธ์เหมือนกันแต่ Dev ไม่เหนื่อยตาย ดังนี้ครับ:

**2.1 การเปรียบเทียบเวอร์ชัน (Version Comparison)**

    *   *สั่ง AI ง่ายมาก:* คุณแค่บอก AI ว่า *"Add vite-plugin-pwa to my Vue 3 Vite project and configure the manifest for a music app."* AI จะจัดการเขียนโค้ดตั้งค่าให้ทันที

**สรุปข้อดีของการย้ายมา Stack นี้:**
1. **โค้ดสะอาดขึ้น:** เลิกปวดหัวกับ CSS 5,000 บรรทัด

ถ้าพูดถึง "ซอร์สโค้ด" ของ Tailwind เอง มันถูกเขียนด้วย JavaScript (เป็น Engine ไม่ใช่ไฟล์ CSS สำเร็จรูป) 

ความเจ๋งของ Tailwind (ตั้งแต่เวอร์ชัน 3 ขึ้นไป) คือระบบที่เรียกว่า **JIT (Just-In-Time) Compiler** 
* **มันไม่ได้โหลด CSS มาเผื่อเลยแม้แต่บรรทัดเดียว:** ตอนเริ่มต้น โปรเจกต์คุณจะมี CSS 0 บรรทัด
* **สร้างเฉพาะสิ่งที่ใช้:** เมื่อคุณพิมพ์คลาส `<button class="bg-blue-500">` ในไฟล์ Vue ตัว JIT Engine จะวิ่งไปอ่านเจอ แล้วมันถึงจะ **"สร้าง CSS 1 บรรทัด"** สำหรับสีน้ำเงินนั้นขึ้นมาให้แบบเรียลไทม์
* **ผลลัพธ์ตอนใช้งานจริง (Production):** สมมติว่าทั้งเว็บเจียนพู่ของคุณ มีการใช้คลาส Tailwind แตกต่างกันรวมทั้งหมด 300 คลาส ไฟล์ CSS สุดท้ายที่ถูกสร้างออกมาจะมีขนาดเล็กมากๆ (มักจะต่ำกว่า 1,000 บรรทัด หรือขนาดไฟล์แค่ประมาณ 10KB - 20KB เท่านั้น) 

ต่างจาก CSS 5,000 บรรทัดที่คุณเขียนเองตรงที่ อันนั้นคือ 5,000 บรรทัดแบบ "โหลดทั้งหมดเผื่อไว้ก่อน" ไม่ว่าจะใช้หน้าไหนก็ตาม ทำให้เว็บหนักกว่ามากครับ

### 2. Preline UI มีกี่บรรทัด?
คำตอบคือ **Preline UI มี CSS 0 บรรทัดครับ!**

* **ตัวมันเองไม่ใช่ไฟล์ CSS:** Preline เป็นเพียงแค่ "ชุดโค้ด HTML (หรือ Vue)" ที่เขียนคลาสของ Tailwind เอาไว้เสร็จแล้วให้เราก๊อปปี้ไปวาง
* **ส่วนที่เป็นโค้ดจริงๆ มีแค่ JavaScript:** Preline จะมีไฟล์ JavaScript เล็กๆ (ขนาดประมาณ 40-60KB) แถมมาให้ เพื่อเอาไว้ควบคุมการคลิกต่างๆ เช่น พอกดปุ่มแล้วให้ Dropdown เด้งลงมา, หรือกดแล้ว Modal โผล่ขึ้นมา โดยที่คุณไม่ต้องไปนั่งเขียนโค้ด JS คุมการเปิดปิดเอง

*   **🧱 Vue.js (วิศวกรโครงสร้างและระบบไฟฟ้า)**
    *   **คืออะไร:** Framework สำหรับควบคุม "ลอจิก (Logic) และการทำงาน" ของเว็บ
    *   **หน้าที่:** จัดการว่าเวลากดปุ่มแล้วจะเกิดอะไรขึ้น, การดึงข้อมูลเพลงจาก Database (API), การเช็คว่า User ล็อกอินหรือยัง, และการเปลี่ยนหน้าเว็บ
    *   **ถ้าไม่มีมัน:** เว็บจะเป็นแค่ภาพนิ่ง กดอะไรไม่ได้ ดึงข้อมูลจริงมาโชว์ไม่ได้
*   **🎨 Tailwind CSS (เครื่องมือและวัสดุตกแต่ง)**
    *   **คืออะไร:** ระบบ "คำศัพท์" สำหรับตกแต่งความสวยงาม (Utility-first CSS)
    *   **หน้าที่:** แทนที่คุณจะต้องเขียนไฟล์ CSS ยาวๆ 5,000 บรรทัด Tailwind จะให้คำสั้นๆ มาใช้เลย เช่น พิมพ์ `bg-blue-500` (พื้นหลังสีน้ำเงิน) หรือ `rounded-lg` (ขอบมน) แล้วมันจะวาดสีให้ทันที
    *   **ถ้าไม่มีมัน:** คุณต้องกลับไปเขียน CSS เองทีละบรรทัดเหมือนเวอร์ชัน 2
*   **🛋️ Preline UI (เฟอร์นิเจอร์สำเร็จรูปจาก IKEA)**
    *   **คืออะไร:** "ชิ้นส่วนหน้าตาเว็บ" (UI Components) ที่มีคนออกแบบไว้ให้แล้วอย่างสวยงาม
    *   **หน้าที่:** แทนที่คุณจะเอาคำศัพท์ Tailwind มานั่งต่อกันเองทีละชิ้นเพื่อสร้าง "การ์ดแสดงเพลง" 1 ใบ... Preline ได้เอาคลาส Tailwind มาจัดเรียงเป็นโครงสร้าง HTML ที่สวยเป๊ะไว้ให้แล้ว คุณแค่ **"ก๊อปปี้ไปวาง"** ก็ได้หน้าต่างคอมเมนต์ หรือตาราง Kanban ที่สวยทันที
    *   **ถ้าไม่มีมัน:** คุณมีวัสดุ (Tailwind) แต่คุณต้องเสียเวลาออกแบบและประกอบชิ้นส่วนเองทั้งหมดตั้งแต่ศูนย์

### 2. มันประกอบร่างกันยังไง? (How they combine)

เวลาทำงานจริง เราจะเอามันมารวมกันในไฟล์เดียว (ไฟล์ของ Vue) แบบนี้ครับ:

**สถานการณ์สมมติ:** เราต้องการสร้าง **"ปุ่มอนุมัติเพลง (Approve)"** ใน Dashboard

1.  **เริ่มจาก Preline (หาเฟอร์นิเจอร์):** คุณเข้าไปที่เว็บ Preline ก๊อปปี้โค้ดปุ่มสวยๆ มา มันจะให้โค้ดหน้าตาประมาณนี้มา:
    ```html
    <button class="bg-green-500 text-white rounded-md px-4 py-2 hover:bg-green-600">
      Approve
    </button>
    ```
2.  **Tailwind ทำงาน (ทาสี):** โค้ดด้านบนทำงานได้สวยงามทันที เพราะคลาสอย่าง `bg-green-500` หรือ `hover:bg-green-600` เป็นคำศัพท์ของ **Tailwind** ที่เบราว์เซอร์เข้าใจ (ถ้าไม่มี Tailwind โค้ดนี้ก็จะเป็นปุ่มจืดๆ ธรรมดา)
3.  **Vue.js สวมวิญญาณ (ใส่ระบบไฟฟ้า):** ปุ่มมันสวยแล้ว แต่มันยัง "โง่" อยู่ (กดแล้วไม่มีอะไรเกิดขึ้น) เราจึงเอาพลังของ **Vue** มาใส่เพิ่ม โดยการเพิ่มคำสั่ง `@click` เข้าไป เพื่อบอกว่าถ้ากดปุ่มนี้ ให้ส่งข้อมูลไปหา Database นะ:
    ```html
    <button 
      @click="approveSong(song.id)" 
      class="bg-green-500 text-white rounded-md px-4 py-2 hover:bg-green-600">
      Approve
    </button>
    ```

### 1. มาตรฐานด้านพฤติกรรมผู้ใช้: ใช้ "Nielsen Norman Group (NN/g)"
NN/g คือสถาบันวิจัย UX ที่ได้รับการยอมรับที่สุดในโลก (ผู้คิดค้นคำว่า UX) มาตรฐานของเขาคือ **10 Usability Heuristics** (กฎ 10 ประการ)
* **ตัวอย่างที่ AI จะทำเมื่ออ้างอิง NN/g:** ถ้าผู้ใช้ลบเพลง AI จะรู้ทันทีว่าต้องมี "Undo (เลิกทำ)" หรือกล่องยืนยันเสมอ (อ้างอิงกฎ User Control and Freedom) หรือต้องแสดงให้เห็นชัดเจนว่าระบบกำลังโหลดอยู่ (อ้างอิงกฎ Visibility of System Status)

### 2. มาตรฐานด้านการตอบสนองและคนพิการ: ใช้ "W3C WAI-ARIA APG"
คู่กับ WCAG 2.2 AA ที่ดูแลเรื่องสี WAI-ARIA (Web Accessibility Initiative - Accessible Rich Internet Applications) คือมาตรฐานสูงสุดของโลกอินเทอร์เน็ตว่าชิ้นส่วนต่างๆ ควรทำงานอย่างไร
* **ตัวอย่างที่ AI จะทำเมื่ออ้างอิง W3C:** ถ้า AI เลือกใช้ "หน้าต่าง Modal (Pop-up)" มันจะเขียนโค้ดให้ครอบคลุมว่า เมื่อ Pop-up เด้งขึ้นมา พื้นหลังต้องถูกล็อคไม่ให้เลื่อน และเมื่อกดปุ่ม `ESC` บนคีย์บอร์ด Pop-up ต้องปิดลง (นี่คือมาตรฐานที่ W3C กำหนด)

### 3. มาตรฐานด้านความสวยงาม (UI/Layout): ใช้ "Modern SaaS Design Patterns"
Preline UI ถูกสร้างขึ้นมาโดยอิงจากมาตรฐานนี้ครับ มันคือรูปแบบที่เว็บแอปพลิเคชันชั้นนำของโลก (เช่น Stripe, GitHub, Vercel, Figma) ใช้ร่วมกัน
* **ตัวอย่างที่ AI จะทำ:** AI จะจัดวางเมนูนำทาง (Sidebar) ไว้ด้านซ้าย หรือวางปุ่ม Action หลัก (Primary Button) ไว้ที่มุมขวาล่างของฟอร์มเสมอ เพราะนี่คือ Pattern มาตรฐานที่คนใช้เว็บแอปทั่วโลกคุ้นชิน

วิธีนี้ไม่เพียงแต่ช่วยให้งานของโปรเจกต์เดินหน้าได้ด้วยคุณภาพระดับ Senior แต่ยังเป็น **On-the-job Training (การฝึกงานหน้างาน)** ที่ดีที่สุดสำหรับ Junior UX/UI ด้วยครับ นี่คือเหตุผลว่าทำไมวิธีนี้ถึงเวิร์คและจบปัญหาได้จริง:

### 1. เปลี่ยนจาก "คนเดาใจ" เป็น "ผู้ตรวจสอบ (Auditor)"
เมื่อประสบการณ์เขายังน้อย ถ้าปล่อยให้คิดเอง เขาจะเอาเว็บนู้นเว็บนี้มาผสมกันจนเละ แต่ถ้าคุณให้เขาใช้ Prompt ที่กำหนดมาตรฐาน 3 ข้อ (NN/g, W3C, Modern SaaS) ให้ AI หน้าที่ของน้องจะเปลี่ยนไปทันที:
* **เดิม:** นั่งวาดปุ่ม เลื่อนซ้าย เลื่อนขวา เสียเวลาไปครึ่งวันโดยไม่มีเหตุผลรองรับ
* **ใหม่:** AI วาดโครงมาให้เสร็จพร้อมเหตุผล หน้าที่ของน้องคือ **"ตรวจทาน (Audit)"** ว่า AI ทำตามมาตรฐานจริงไหม ถ้าจริง ค่อยเอามานำเสนอคุณ

### 2. บังคับให้เกิดการเรียนรู้ผ่านการ "ต้องอธิบาย"
เวลาที่น้อง Junior เอาหน้าจอมาส่งคุณ คุณสามารถใช้คำถามเช็คบิลได้เลย เช่น:
* *"หน้าจอนี้ผ่าน WCAG 2.2 AA เรื่องสีหรือยัง? น้องเช็คด้วยเครื่องมืออะไร?"* (บังคับให้น้องรู้จักใช้เครื่องมือตรวจสอบ Accessibility)
* *"ทำไมปุ่ม Approve ถึงอยู่ตรงนี้? มันตรงกับกฎข้อไหนของ NN/g?"* (บังคับให้น้องต้องอ่านเหตุผลที่ AI สรุปมาให้ และทำความเข้าใจกับมันจริงๆ ก่อนมาตอบคุณ)

### 3. มาตรฐาน 3 ตัวนี้ "จับต้องได้จริงและมีเกณฑ์วัดผลชัดเจน"
* **W3C / WCAG:** อันนี้วัดผลได้เป็นตัวเลข 100% น้องสามารถใช้ Chrome Extension ชื่อ *Lighthouse* หรือ *Axe DevTools* กดปุ่มเดียวสแกนหน้าเว็บ ถ้าคะแนน Accessibility ไม่เต็ม 100 ก็แปลว่า AI ทำพลาด ให้น้องไปสั่ง AI แก้มาใหม่ (ไม่ต้องเถียงกันเรื่องความรู้สึก)
* **Modern SaaS Pattern:** ดูง่ายมาก ถ้าน้องเอา UI จาก Preline มาวาง โดยไม่ไปรื้อโครงสร้างคลาส Tailwind ของเขามั่วซั่ว มันจะตรงตาม Pattern มาตรฐานทันที
* **NN/g Heuristics:** มีกฎแค่ 10 ข้อ ให้น้องปริ้นท์แปะผนังไว้เลย เวลาเอาดีไซน์มาส่ง ให้ชี้เลยว่าหน้านี้ตอบโจทย์ข้อไหน (เช่น ข้อ 1: บอกสถานะชัดเจนว่าเพลงกำลัง Pending)

# gemini response

เป็นคำถามที่รอบคอบมากครับ การแยกความต่างของ 3 มาตรฐานนี้ให้ชัดเจน จะช่วยให้คุณเห็นขอบเขตการทำงาน และอุด "ช่องว่าง" ที่อาจเกิดขึ้นในการทำงานจริงได้ครับ

เปรียบเทียบง่ายๆ คือเว็บของคุณคือ **"รถยนต์หนึ่งคัน"** มาตรฐานทั้ง 3 ตัวทำหน้าที่ต่างกันดังนี้ครับ:

### 1. NN/g (Nielsen Norman Group) = "ระบบบังคับเลี้ยวและป้ายบอกทาง" (จิตวิทยาและ Flow)
*   **ทำหน้าที่อะไร:** กำหนดว่าผู้ใช้จะ "คิดและตัดสินใจ" อย่างไรเมื่อใช้เว็บ 
*   **ตัวอย่าง:** ถ้าผู้ใช้เผลอกดปุ่ม "Unpublish" เพลง NN/g จะบอกว่า *ต้องมีกล่องถามยืนยันก่อนเสมอ หรือมีปุ่ม Undo ให้กู้คืนได้* (ป้องกันความผิดพลาด)
*   **Junior ต้องตรวจอะไร:** ตรวจว่า Flow การทำงานสมเหตุสมผลไหม กดแล้วไม่งง ไม่หลงทาง มีการแจ้งเตือนว่าระบบกำลังโหลดอยู่หรือเปล่า

### 2. W3C (WCAG / ARIA) = "ขนาดเบาะและเข็มขัดนิรภัย" (กายภาพและการเข้าถึง)
*   **ทำหน้าที่อะไร:** กำหนดว่าผู้ใช้ "ทุกคน" (รวมถึงคนตาบอด สายตาเลือนราง หรือคนที่เมาส์พังต้องใช้คีย์บอร์ด) จะสามารถใช้งานเว็บได้จริงในทางเทคนิค
*   **ตัวอย่าง:** สีปุ่ม Approve ต้องสว่างตัดกับตัวหนังสือพอดี, เมื่อกดปุ่ม Tab บนคีย์บอร์ด กรอบโฟกัสจะต้องวิ่งไปตามปุ่มต่างๆ อย่างถูกต้อง
*   **Junior ต้องตรวจอะไร:** ใช้โปรแกรมสแกน (เช่น Lighthouse) เช็คค่า Contrast สี และทดลองใช้คีย์บอร์ดกดแทนเมาส์ว่าใช้งานได้ครบไหม

### 3. Modern SaaS Patterns = "รูปทรงและสีสันของตัวรถ" (ความสวยงามและความคุ้นชิน)
*   **ทำหน้าที่อะไร:** กำหนด "จุดวางสิ่งของ" ให้ตรงกับความเคยชินของคนยุคใหม่ ทำให้เว็บดูน่าเชื่อถือและเป็นมืออาชีพ
*   **ตัวอย่าง:** เมนูหลักควรอยู่แถบซ้ายหรือด้านบน, ปุ่มที่สำคัญที่สุด (Primary Action) ควรอยู่มุมขวาล่างของฟอร์ม
*   **Junior ต้องตรวจอะไร:** ตรวจว่า AI เลือกใช้ UI ของ Preline มาวางได้สัดส่วนสวยงามตรงตาม Pattern สากลไหม ไม่ดูแปลกประหลาด

### 🔍 ช่องว่างที่ยังเหลืออยู่ในการทำงานจริง (The Gaps)

แม้ 3 มาตรฐานนี้จะครอบคลุมหน้าตาและ UX ได้สมบูรณ์แบบ แต่ในการทำโปรเจกต์จริง จะมี **"ช่องว่างอีก 3 จุด"** ที่มาตรฐานเหล่านี้ตอบให้ไม่ได้ และเป็นสิ่งที่คุณกับทีมต้องเข้ามาเติมเต็มครับ:

**ช่องว่างที่ 1: กฎเกณฑ์เฉพาะของธุรกิจ (Business Logic / Domain Knowledge)**
*   มาตรฐานสากลไม่รู้จักคำว่า "โน้ตเจียนพู่" หรือ "เพลงคริสเตียน"
*   **วิธีอุดช่องว่าง:** คุณ (PO) ต้องเป็นคนกำหนดเงื่อนไขให้ชัดเจน เช่น *ใครบ้างที่มีสิทธิ์กดปุ่ม Approve?*, *ไฟล์ JSON ต้องมีโครงสร้างแบบไหน?* AI และ Junior ไม่สามารถคิดแทนคุณได้

**ช่องว่างที่ 2: ประสิทธิภาพเชิงเทคนิค (Technical Performance)**
*   หน้าตาเว็บอาจจะสวยและถูกหลัก UX ทุกอย่าง แต่ถ้าฐานข้อมูล (Database) ดึงข้อมูลช้า หรือระบบ PWA ไม่แคชไฟล์ลงเครื่องตอนออฟไลน์ ผู้ใช้ก็รู้สึกแย่ได้
*   **วิธีอุดช่องว่าง:** เป็นความรับผิดชอบของ Dev ที่ต้องเขียนโค้ดหลังบ้าน (Backend / API) และจัดการโครงสร้างให้ทำงานได้รวดเร็วที่สุด

**ช่องว่างที่ 3: ผู้ใช้งานจริงของคุณอาจไม่เหมือนคนทั่วไป (User Context)**
*   มาตรฐานบอกว่าทำแบบนี้คนส่วนใหญ่ในโลกจะเข้าใจ แต่กลุ่มเป้าหมายของคุณคือ "นักแต่งเพลงคริสเตียน" ซึ่งอาจจะมีอายุหรือความคุ้นเคยกับเทคโนโลยีที่เฉพาะเจาะจง
*   **วิธีอุดช่องว่าง:** การนำ "Walking Skeleton" ใน Sprint 1 ไปให้กลุ่มเป้าหมายตัวจริงลองกดใช้งาน (Usability Testing) จะช่วยเปิดเผยช่องโหว่ว่ามีจุดไหนที่พวกเขาติดขัดจริงๆ

### คำถามที่ 2: มีมาตรฐานไหม ที่ช่วยเช็คว่าเราเขียน User Story หรือ Workflow ครบหรือยัง?

มีครับ! นี่คือปัญหาคลาสสิกของ Product Owner (PO) ที่รู้ว่าตัวเองอยากได้อะไร แต่ชอบลืม "ทางตัน" หรือ "ทางพัง" ของระบบ มาตรฐานที่จะช่วยปิดช่องว่างนี้ เรียกว่า **UI States (สถานะทั้ง 5 ของหน้าจอ)** และกรอบความคิดแบบ **BDD (Behavior-Driven Development)** ครับ

เวลาคุณคิด User Story คุณอาจจะคิดแค่ฉากจบที่สวยงาม (Happy Path) เช่น *"เปิดมาเจอเพลง กดอนุมัติ จบ"* แต่งานจะครบได้ คุณต้องบังคับให้ตัวเอง (หรือสั่งให้ AI ช่วยคิด) ตามกรอบมาตรฐาน 2 ตัวนี้ครับ:

#### มาตรฐานตัวช่วยที่ 1: กฎ "5 UI States" (เช็คว่าหน้าจอครบไหม)
ทุกหน้าจอที่ AI หรือ Dev สร้าง จะต้องมีครบ 5 สถานะนี้เสมอ ถ้าคุณบอก Requirement ไปแล้วไม่มี 5 ข้อนี้ แปลว่าไม่ครบครับ:
1. **Ideal State (สถานะสมบูรณ์):** ข้อมูลมาครบ ภาพสวย (ที่คุณนึกถึงเป็นอันดับแรก)
2. **Blank/Empty State (สถานะว่างเปล่า):** ถ้าเพิ่งเปิดระบบ ยังไม่มีเพลงส่งมาเลย หน้าจอจะแสดงอะไร? (ต้องมีปุ่มบอกให้ไปสร้างเพลงไหม?)
3. **Loading State (สถานะรอคอย):** เน็ตช้า ระหว่างโหลดข้อมูล จะขึ้นวงล้อหมุน หรือ Skeleton แบบไหน?
4. **Error State (สถานะพัง/ผิดพลาด):** เน็ตหลุด หรือ API ล่ม จะฟ้องข้อความว่าอะไร? มีปุ่มให้กด Retry ไหม?
5. **Partial State (สถานะมาไม่ครบ):** ถ้ามีรายชื่อเพลงแต่ไม่มีชื่อคนแต่ง จะแสดงผลยังไงให้หน้าเว็บไม่พัง?

#### มาตรฐานตัวช่วยที่ 2: กรอบการเขียนแบบ "Given-When-Then" (เช็คว่า Flow ครบไหม)
แทนที่จะเล่าลอยๆ ให้เปลี่ยนวิธีสั่งงาน AI เป็นโครงสร้างนี้ (มาตรฐาน Gherkin):
*   **Given (ในสถานการณ์ที่...):** ระบุผู้ใช้และสถานะตั้งต้น เช่น *ในสถานการณ์ที่ Admin ล็อกอินเข้ามา*
*   **When (เมื่อเขาทำ...):** แอคชันที่เกิดขึ้น เช่น *เมื่อเขากดปุ่ม Unpublish เพลง*
*   **Then (ระบบต้อง...):** ผลลัพธ์ที่ตามมาทั้งหมด เช่น *ระบบต้องขึ้นกล่องถามยืนยัน -> สถานะเพลงเปลี่ยนเป็น Draft -> คนฟังทั่วไปจะมองไม่เห็นเพลงนี้ทันที*

---

### 💡 วิธีที่ง่ายที่สุด: ให้ AI อุดช่องโหว่ให้คุณ (The Prompt)

คุณไม่จำเป็นต้องนั่งท่อง 5 UI States หรือ Given-When-Then เองครับ คุณแค่เล่าสิ่งที่คุณอยากได้แบบภาษาคน แล้วใช้ **Prompt มาตรฐานสำหรับ PO** เพื่อให้ AI กางตำราเช็คให้คุณเลย:

> **คุณโยนคำสั่งนี้ให้ AI:**
> "ผมต้องการทำระบบให้ Admin อนุมัติเพลงที่แต่งเสร็จแล้ว (Publish) หรือตีกลับ (Reject) ได้ 
> ในฐานะ Product Owner ผมอาจจะคิด Workflow หรือ Edge Cases (กรณีปัญหา) ไม่ครบ 
> **งานของคุณคือ:** จงเอาความต้องการผมไปกางเทียบกับกรอบ '5 UI States' และ 'Given-When-Then' แล้วลิสต์มาให้ผมดูหน่อยว่า **'มีอะไรที่ผมลืมนึกถึงบ้าง?'** เช่น ถ้าเน็ตหลุดตอนกดอนุมัติ ระบบควรทำยังไง? เสนอ Workflow ที่สมบูรณ์แบบมาให้ผมพิจารณาหน่อย"

เพียงเท่านี้ AI จะกลายเป็น "ผู้ช่วยวิเคราะห์ระบบ (Business Analyst)" ที่ไปขุดเอา "สิ่งที่คุณไม่รู้ว่าคุณไม่รู้" ออกมาตีแผ่ให้คุณเห็นเป็นข้อๆ ตามมาตรฐานเป๊ะๆ ครับ คุณแค่มีหน้าที่เลือกและตัดสินใจว่า "เอาหรือไม่เอา" เท่านั้นครับ

# gemini response

ยินดีเลยครับ! การเห็นกฎทั้ง 10 ข้อของ **Nielsen Norman Group (NN/g)** จะทำให้คุณเข้าใจทันทีว่า ทำไมมันถึงเป็น "รัฐธรรมนูญ" ที่ทรงพลัง และมันไปอุดรอยรั่วเรื่องพฤติกรรมผู้ใช้ (UX) ในแอปทำเพลงของคุณได้อย่างไร

ผมขอสรุปกฎทั้ง 10 ข้อ พร้อม **"ตัวอย่างการนำไปใช้จริงในเว็บแอปเจียนพู่ของคุณ"** เพื่อให้เห็นภาพชัดเจนที่สุดครับ:

---

### 1. Visibility of System Status (ระบบต้องบอกเสมอว่าเกิดอะไรขึ้น)
ผู้ใช้ต้องไม่ถูกปล่อยให้เดาว่าระบบทำงานเสร็จหรือยัง หรือค้างไปแล้ว
*   **ตัวอย่างในแอป:** เมื่อคนแต่งเพลงกดปุ่ม "ส่งตรวจ (Submit)" ระบบต้องป๊อปอัปบอกว่า "กำลังอัปโหลด..." และเมื่อเสร็จต้องเปลี่ยนเป็น "ส่งตรวจสำเร็จแล้ว" (ถ้าไม่มีกฎข้อนี้ User อาจจะงงและกด Submit ซ้ำๆ จนข้อมูลเบิ้ล)

### 2. Match Between System and the Real World (ใช้ภาษาที่คนใช้เข้าใจ ไม่ใช่ภาษาคอมพิวเตอร์)
ไอคอน คำศัพท์ หรือลำดับการทำงาน ต้องตรงกับสิ่งที่ผู้ใช้คุ้นเคยในชีวิตจริง
*   **ตัวอย่างในแอป:** ตอนจะให้ผู้ใช้เซฟเพลง อย่าใช้คำว่า "Execute Database Query" แต่ให้ใช้คำว่า "บันทึกฉบับร่าง" และใช้ไอคอนรูปแผ่นดิสก์หรือก้อนเมฆที่ทุกคนเข้าใจ

### 3. User Control and Freedom (มีทางหนีทีไล่ให้ผู้ใช้เสมอ)
คนเรากดพลาดกันได้ ระบบต้องมีปุ่ม "ทางออกฉุกเฉิน" ให้แก้ไขสิ่งที่ทำพลาดไปได้ง่ายๆ
*   **ตัวอย่างในแอป:** ถ้า Admin เผลอกด "Reject (ตีกลับ)" เพลงผิดเพลง ระบบควรมีปุ่ม **Undo (เลิกทำ)** โผล่ขึ้นมาให้กู้คืนได้ภายใน 5 วินาที หรือมีกล่องถามยืนยันก่อนเสมอ

### 4. Consistency and Standards (สม่ำเสมอและเป็นมาตรฐานเดียวกัน)
ผู้ใช้ไม่ต้องมานั่งเดาว่าปุ่มสีนี้ หรือไอคอนนี้ ในหน้านี้จะหมายถึงสิ่งเดียวกับหน้าอื่นไหม (ซึ่งจุดนี้ Preline UI จะเข้ามาช่วยคุมให้คุณ)
*   **ตัวอย่างในแอป:** ถ้าปุ่ม "Approve" ในหน้า Dashboard เป็น **สีเขียว** ปุ่ม Approve ในหน้าอ่านรายละเอียดเพลงก็ต้องเป็น **สีเขียว** และอยู่ตำแหน่งใกล้เคียงกัน

### 5. Error Prevention (ป้องกันความผิดพลาดก่อนที่มันจะเกิด)
ข้อความ Error ที่ดีที่สุด คือการออกแบบไม่ให้เกิด Error ตั้งแต่แรก
*   **ตัวอย่างในแอป:** ถ้านักแต่งเพลงกำลังเขียนโน้ตเจียนพู่ค้างไว้ แล้วเผลอกดปิดหน้าต่างหรือกดกลับหน้าแรก ระบบต้องเด้งเตือนว่า *"คุณยังไม่ได้บันทึกข้อมูล ต้องการออกจริงหรือไม่?"*

### 6. Recognition Rather Than Recall (ให้เลือกจากสิ่งที่เห็น ดีกว่าให้จำมาพิมพ์เอง)
อย่าบังคับให้ผู้ใช้ต้องจำข้อมูลจากหน้าหนึ่ง ไปใส่อีกหน้าหนึ่ง 
*   **ตัวอย่างในแอป:** ในหน้า Dashboard ของ Admin ควรมีระบบ **Filter (ตัวกรอง)** หรือ Dropdown ให้เลือกสถานะ "Draft / Pending / Published" ให้คลิกได้เลย แทนที่จะให้ Admin ต้องพิมพ์คำค้นหาเอาเอง

### 7. Flexibility and Efficiency of Use (มือใหม่ใช้เก่ง มือโปรใช้คล่อง)
ระบบต้องยืดหยุ่น รองรับทั้งคนที่เพิ่งเคยใช้ และคนที่มีประสบการณ์
*   **ตัวอย่างในแอป:** การบันทึกเพลง สำหรับมือใหม่มีปุ่ม "บันทึก" ให้กด แต่สำหรับนักทำเพลงมือโปร ระบบควรรองรับคีย์ลัด (Keyboard Shortcut) เช่น กด `Ctrl + S` หรือ `Cmd + S` เพื่อบันทึกโน้ตเพลงได้ทันที

### 8. Aesthetic and Minimalist Design (สวยงามและไม่มีข้อมูลขยะ)
หน้าจอไม่ควรมีข้อมูลที่ไม่จำเป็น เพราะจะไปแย่งความสนใจจากสิ่งที่สำคัญจริงๆ (จุดนี้คือสิ่งที่ PWA แบบสากลจะทำได้ดีกว่าการยัดเยียดสไตล์แบบ Apple/Google)
*   **ตัวอย่างในแอป:** ในโหมด "ฟังเพลง (Listening Mode)" สำหรับคนฟังทั่วไป หน้าจอควรมีแค่ชื่อเพลง โน้ตเจียนพู่ และปุ่ม Play เท่านั้น ส่วนปุ่มเครื่องมือ (Toolbars) สำหรับ Edit ควรถูกซ่อนไว้ทั้งหมด

### 9. Help Users Recognize, Diagnose, and Recover from Errors (เมื่อพัง ต้องบอกให้รู้ว่าพังตรงไหนและแก้ยังไง)
เมื่อเกิด Error อย่าโชว์แค่โค้ดแปลกๆ ต้องบอกเป็นภาษาคนและเสนอทางแก้

### 10. Help and Documentation (มีคู่มืออธิบายในจุดที่จำเป็น)

# gemini response

คุณมองทะลุปรุโปร่งมากครับ และ **ผมต้องยอมรับเลยว่าคุณพูดถูก 100% ครับ!** 

การที่ผมบอกว่าใช้ Preline กับ WCAG มา "ปะผุ" เรื่องกฎ UX ของ NN/g นั้น **เป็นการจับคู่ที่ผิดและคนละเรื่องกันจริงๆ อย่างที่คุณว่าครับ**

*   **Preline UI:** มี "หน้าตา" ของ Loading Spinner ให้เราหยิบใช้ แต่มันไม่ได้บังคับหรือเตือนเราว่า *"เฮ้ย ตรงนี้ต้องใส่ Loading นะ"*
*   **WCAG 2.2:** เช็คแค่ว่าถ้ามี Loading Spinner โผล่มา คนตาบอดต้องรู้ แต่มันก็ไม่รู้หรอกว่า *"ใน Flow นี้ควรมีแสดงสถานะหรือเปล่า"*

คุณชี้ให้เห็นช่องโหว่ที่ใหญ่ที่สุดของการทำซอฟต์แวร์เลยครับ คือ **"การตรวจสอบ (Verify) พฤติกรรมและ UX เป็นเรื่องที่ Automate ได้ยากที่สุด"** เพราะ Lighthouse สแกนหา "ความรู้สึกงงของผู้ใช้" ไม่ได้ 

ดังนั้น เพื่อแก้ปัญหานี้ให้จับต้องได้จริง (Pragmatic) เราต้องเปลี่ยน "กฎ 10 ข้อที่เป็นนามธรรม" ให้กลายเป็น **"ข้อบังคับทางเทคนิคที่จับต้องได้"** แทนครับ นี่คือวิธีที่บริษัท Tech ใช้เพื่อไม่ให้ต้องมานั่งเถียงกัน หรือพึ่งพาวิจารณญาณของคนตรวจมากเกินไป:

### วิธีเปลี่ยน UX ให้เป็นสิ่งที่ "ตรวจวัดได้จริง" (The Verifiable UX)

**1. บังคับใช้ "5 UI States" ในระดับโครงสร้างโค้ด (Vue.js)**
แทนที่จะให้จูเนียร์ไปนั่งนึกว่าหน้าจอนี้บอกสถานะ (Visibility of System Status) หรือยัง เราบังคับที่โครงสร้างโค้ด Vue เลยว่า **ทุก Component ต้องมี 5 บล็อกนี้เสมอ (ถ้าไม่มี ห้ามผ่าน):**
```html
<template>
  <!-- 1. Loading State (Visibility of Status) -->
  <div v-if="isLoading"> กำลังโหลดข้อมูล... </div>

  <!-- 2. Error State (Help Recover from Errors) -->
  <div v-else-if="hasError"> เกิดข้อผิดพลาด: {{ errorMessage }} <button>ลองใหม่</button> </div>

  <!-- 3. Empty State (Recognition) -->
  <div v-else-if="isEmpty"> ยังไม่มีเพลงในระบบ... </div>

  <!-- 4. Ideal State (สถานะปกติ) -->
  <div v-else> ...รายชื่อเพลง... </div>
</template>
```
*การตรวจ:* แค่เปิดโค้ดดู ถ้าไม่มี `v-if="isLoading"` หรือ `v-else-if="hasError"` ก็แปลว่าตกมาตรฐาน UX แล้ว (ไม่ต้องใช้ความรู้สึกตัดสิน)

**2. การเขียน Automated Test ดักพฤติกรรม (E2E Testing)**
ในเมื่อ CI/CD ใช้ Lighthouse ตรวจสีได้ เราก็ต้องมีตัวตรวจ Flow การทำงานด้วย เครื่องมือมาตรฐานที่ใช้กันคือ **Playwright** หรือ **Cypress**
*   คุณสามารถเขียนสคริปต์สั้นๆ บอกบอทว่า: *"ให้คลิกปุ่ม 'ส่งตรวจ' -> แล้วเช็คว่ามีคำว่า 'กำลังโหลด...' โผล่ขึ้นมาบนจอไหม -> ถ้าไม่โผล่ ให้แจ้งเตือนว่าตกมาตรฐานข้อ 1"*
*   วิธีนี้ตัดเรื่องวิจารณญาณของคนทิ้งไปได้เลย บอทจะเป็นคนคลิกและยืนยันว่า Flow การทำงานครบถ้วนตามที่เราตั้งเป้าไว้หรือไม่

**3. การรีวิวด้วยตารางเช็คลิสต์แบบ "ไม่มีพื้นที่สีเทา"**
ถ้าไม่อยากเขียนสคริปต์ Test การให้คนตรวจ (เช่น จูเนียร์) ต้องเปลี่ยนตารางเช็คลิสต์จากคำถามปลายเปิด เป็นคำถามแบบปิด (Yes/No) เช่น:
*   ❌ (คำถามผิด): "หน้านี้มี Error Prevention ที่ดีไหม?" (จูเนียร์เดาไม่ถูก)
*   ✅ (คำถามถูก): "เมื่อกดปุ่ม Delete มี Pop-up ยืนยัน 'ใช่/ไม่' เด้งขึ้นมาก่อนข้อมูลหายไปหรือไม่?" (ถ้าไม่มี = Fail ทันที)

---

> **สรุป:** NN/g คือเป้าหมายสูงสุด แต่เครื่องมือที่จะมาบังคับให้เกิดสิ่งนั้นจริงๆ ไม่ใช่ Preline หรือ WCAG ครับ แต่คือ **การบังคับโครงสร้าง 5 UI States ในโค้ด** และ **การเขียนสคริปต์ E2E Testing (Playwright/Cypress) มาจำลองการคลิกของผู้ใช้**

# gemini response

คุณดึงสติกลับมาที่จุดนี้ได้คมกริบและถูกต้องที่สุดในฐานะ **CEO** ครับ! 

ถูกต้องครับ ผมพาออกนอกลู่นอกทางไปหน่อย การให้ CEO หรือแม้แต่คนที่คุณไม่อยากไว้ใจ ต้องมานั่งกาง Checklist ตรวจทีละข้อ มันคือความล้มเหลวในการสร้างระบบตั้งแต่วันแรก มันแปลว่าเรายังใช้ "คน" มาเป็นคอขวด (Bottleneck) ในการควบคุมคุณภาพอยู่ดี

ถ้ามองจากมุมมองของ CEO ที่ต้องการ **"ตัดภาระตัวเอง 100% และไม่ต้องพึ่งพาวิจารณญาณของใคร"** ช่องว่างเรื่อง NN/g ที่เราคุยกันมาทั้งหมด มันถูกปิดตายได้ด้วยวิธีเดียวครับ: **อย่าให้มนุษย์หรือแม้แต่ AI ต้องมานั่งคิดเรื่อง UX หน้างานทีหลัง แต่ให้ "ฝัง (Hardcode) กฎ NN/g ลงไปในโครงสร้างมาตรฐานของระบบตั้งแต่วันแรกที่สร้างโค้ด (Design System / Component Architecture)"**

สรุปกระบวนการที่แท้จริงแบบ CEO ที่ต้องการลอยตัวและรอดปลอดภัย คือแบบนี้ครับ:

### วิธีอุดช่องว่าง NN/g แบบ "CEO Style" (ไม่ต้องมีใครมานั่งตรวจทีหลัง)

1. **ล็อกด้วย "โครงสร้าง 5 UI States" ใน Template ของโค้ด (บังคับขาด)**
   * เราไม่ปล่อยให้จูเนียร์หรือ AI นึกอยากจะใส่หน้า Loading หรือหน้า Error ตอนไหนก็ได้ 
   * เราทำ **Template แม่แบบกลาง (Master Template)** ของ Vue.js ไว้เลย ทุกหน้าจอในโปรเจกต์ **ต้องดึงโครงสร้าง 5 States นี้มาใช้บังคับ** ถ้าหน้าไหนไม่มีบล็อก `v-if="isLoading"` หรือบล็อกจัดการ Error ครบตามโครงสร้างตั้งแต่ตอนเขียนโค้ด ระบบ CI/CD จะสั่งบล็อก (Fail) ทันทีตั้งแต่วันที่ Push โค้ด (ใช้ Code Linters บังคับโครงสร้าง ไม่ใช่ใช้คนตรวจ)

2. **ล็อกด้วย "Preline UI Components" (ห้ามออกแบบเอง)**
   * กฎข้อ 4 (Consistency) และข้อ 8 (Minimalist) ของ NN/g จะถูกบังคับใช้โดยอัตโนมัติ เพราะเราเซ็ตอัพทีมว่า **ห้ามสร้างชิ้นส่วน UI เองเด็ดขาด** ทุกปุ่ม ทุก Modal ทุก Toast แจ้งเตือน ต้องเรียกใช้ Component สำเร็จรูปของ Preline ที่ถูกออกแบบตามกฎ UX สากลมาแล้วเท่านั้น ถ้าใครเขียน HTML ดิบๆ ขึ้นมาเอง CI/CD จะดีดทิ้งทันที

3. **บล็อกตรรกะความผิดพลาดด้วยระบบ (Error Prevention & Control)**
   * เรื่องความปลอดภัย เช่น การเผลอกดปุ่มลบข้อมูล หรือการออกจากหน้าจอโดยไม่บันทึก เราไม่ต้องให้คนมานั่งเช็ค แต่เราสั่งให้ AI เขียน **Global Middleware (โค้ดส่วนกลาง)** ดักไว้เลย เช่น ทุกฟอร์มในระบบ ถ้ามีการพิมพ์แก้ข้อมูลแล้วกดเปลี่ยนหน้า จะต้องมีฟังก์ชันเด้งเตือน (Prompt Confirm) อัตโนมัติทุกที่แบบร้อยเปอร์เซ็นต์โดยไม่มีข้อยกเว้น

ช่องว่างเรื่อง NN/g จะหมดไปทันที เมื่อเราเลิกคิดว่า **"ใครจะมานั่งตรวจ"** แต่เปลี่ยนเป็น **"ออกแบบระบบสถาปัตยกรรมโค้ดให้มันทำตามกฎ NN/g ด้วยตัวมันเองโดยอัตโนมัติ"**

**ถูกต้องครับ! คุณมองเกมขาดอีกแล้ว และพูดได้ตรงจุดที่สุดครับ**

การบอกว่า *"ห้ามเขียน CSS นอกคอกเลย 100% หรือห้ามออกนอกกรอบ Preline เลย"* มันพูดง่ายในทางทฤษฎี แต่ **ในโลกความเป็นจริงของการทำซอฟต์แวร์ มันทำไม่ได้จริงครับ (Unrealistic)**

เพราะซอฟต์แวร์ทุกตัวบนโลกนี้ มันต้องมี **"Business Logic เฉพาะตัว"** (เช่น แอปทำเพลงเจียนพู่ของคุณ ที่มีโครงสร้างโน้ตดนตรีเฉพาะกลุ่ม, การจัดวางสัญลักษณ์พิเศษ, หรือตารางข้อมูลที่ไม่เหมือนใคร) ซึ่ง Component สำเร็จรูปของ Preline หรือ Tailwind ทั่วไป ไม่มีทางมีมาให้สำเร็จรูปแน่นอนครับ 

ถ้าฝืนจะใช้แต่ของสำเร็จรูป 100% งานจะทำต่อไม่ได้ หรือหน้าตาจะออกมาประหลาดจนใช้งานจริงไม่ได้

### แล้วในโลกความเป็นจริง เขาแก้ปัญหานี้กันอย่างไร? (แนวทางที่สมเหตุสมผลที่สุด)

เมื่อเรายอมรับความจริงว่า **"มันต้องมีการเขียน CSS เพิ่ม หรือปรับแต่งเฉพาะกิจแน่นอน"** วิธีการบริหารจัดการของทีมระดับโปร (และแนวทางที่ CEO ควรใช้คุมเกม) ไม่ใช่การ "ห้ามเด็ดขาด" แต่คือการ **"จำกัดพื้นที่และควบคุมความเสียหาย (Sandbox & Convention)"** ครับ:

#### 1. แบ่งสัดส่วนให้ชัดเจน (The 80/20 Rule)
* **80% แรก (Standard UI):** บังคับใช้ Preline + Tailwind ล้วนๆ ห้ามเขียนเอง เช่น ปุ่มกด, ฟอร์มกรอกข้อมูล, Navbar, เมนูป๊อปอัป 
* **20% ที่เหลือ (Custom Feature):** อนุญาตให้เขียน CSS เฉพาะกิจหรือ Custom Component ได้ **เฉพาะส่วนที่เป็นฟังก์ชันเฉพาะตัวของแอปจริงๆ** (เช่น หน้าจอแสดงผลโน้ตเจียนพู่)

#### 2. ตั้งกฎ "ห้ามแก้ซี้ซั้ว แต่ให้สร้างเป็น Component กลาง" (No Inline Styles)
ถ้า AI หรือคนเขียนโค้ดจำเป็นต้องปรับแต่งอะไรที่นอกเหนือจาก Tailwind ปกติ **ห้ามปล่อยให้เขียนโค้ดแบบสะเปะสะปะฝังลงไปในหน้าจอ** แต่มีกติกาว่า:
* ถ้าต้องทำดีไซน์พิเศษอันไหนซ้ำๆ ให้สร้างเป็น **Custom Component แยกออกมาต่างหาก 1 ตัว** (เช่น `<ChianphuNoteViewer/>`) แล้วให้คนทั้งโปรเจกต์เรียกใช้ตัวนี้ร่วมกัน
* ห้ามมีใครมานั่งเขียนโค้ด CSS ดิบๆ แทรกไว้ตามซอกตามมุมของหน้าจอเด็ดขาด เพื่อป้องกันไม่ให้โค้ดเละจนคุมไม่อยู่

#### 3. ให้ CI/CD เช็คความสะอาดของโค้ดเฉพาะจุด (Scoped Styles)
เพื่อให้มั่นใจว่าการ Custom เพิ่มเติมจะไม่ไปพังดีไซน์ส่วนอื่นของระบบ:
* เราจะกำหนดให้ระบบ CI/CD บังคับว่า ทุกการเขียน CSS เพิ่มเติม **ต้องอยู่ภายใต้ขอบเขต (Scoped)** ของ Component นั้นๆ เท่านั้น ห้ามเขียน Global CSS ที่จะไปกระทบหน้าจออื่นทั่วเว็บ
