## Q
งานของเรา: เว็บแอปคลังเพลงนมัสการสำหรับโบสถ์ไทย มีกระดานติดตามสถานะเพลง (workflow/status board) ให้ทีมงานเล็กๆ เห็นว่าเพลงไหนอยู่ขั้นไหน (ร่าง / กำลังแก้ / รอตรวจ / เผยแพร่แล้ว) และแต่ละขั้นมีกี่เพลง คำถาม: จากหนังสือ Information Architecture (Morville) และ Web Bloopers (Johnson) เท่านั้น มีหลักการหรือข้อควรระวังอะไรที่ใช้กับกระดานแบบนี้โดยตรง? บังคับ: ทุกข้อต้องระบุ (ก) ชื่อหนังสือ (ข) เลขบท หรือเลข Blooper (ค) เลขหน้าที่พิมพ์ในเล่ม ถ้าข้อไหนบอกเลขหน้าไม่ได้ให้เขียนว่า NO PAGE ห้ามเดาเลขหน้า ตอบไม่เกิน 8 ข้อ เอาข้อที่ตรงที่สุด

## A
หลักการและข้อควรระวังสำหรับกระดานติดตามสถานะเพลง (workflow board) จากหนังสือทั้งสองเล่ม มีดังนี้:

1.  **การใช้ Metadata ระบุสถานะ (Status Metadata):** ในการจัดการระบบคลังข้อมูล จำเป็นต้องมี Metadata เพื่อระบุสถานะ (Status) ของแต่ละรายการ เช่น "active", "deleted", "inactive" หรือ "suggestion" เพื่อใช้ในกระบวนการจัดการเนื้อหา (Content Management) ซึ่งในกรณีนี้คือการระบุว่าเพลงอยู่ขั้นร่าง หรือเผยแพร่แล้ว [1]
    *   (ก) ชื่อหนังสือ: Information Architecture
    *   (ข) เลขบท: Chapter 20
    *   (ค) เลขหน้า: **NO PAGE**

2.  **การใช้เครื่องมือช่วยบอกลำดับ (Sequential Aids):** ระบบควรมีเบาะแสที่ช่วยให้ผู้ใช้ทราบว่าเนื้อหา (เพลง) นั้นอยู่ขั้นตอนใดในกระบวนการ และยังเหลืออีกกี่ขั้นตอนกว่าจะเสร็จสิ้น (เช่น "step 3 of 8") เพื่อให้ทีมงานเห็นภาพรวมของ Workflow ได้ชัดเจน [2]
    *   (ก) ชื่อหนังสือ: Information Architecture
    *   (ข) เลขบท: Chapter 4
    *   (ค) เลขหน้า: **NO PAGE**

3.  **กฎและบทบาทในขั้นตอนการทำงาน (Rules and Roles):** กระบวนการทำงาน (Workflow) ต้องมีการกำหนดกฎเกณฑ์ในการสร้าง แก้ไข และเผยแพร่เนื้อหา รวมถึงต้องกำหนดบทบาท (Roles) ของทีมงานให้ชัดเจนว่าใครมีหน้าที่เขียน ใครมีหน้าที่ตรวจ (Review) หรือใครเป็นคนจัดการ Metadata [3]
    *   (ก) ชื่อหนังสือ: Information Architecture
    *   (ข) เลขบท: Chapter 11
    *   (ค) เลขหน้า: **NO PAGE**

4.  **ระบบการจัดหมวดหมู่ (Organization Systems):** การจัดกลุ่มเพลงตามขั้นตอนการทำงาน (Workflow stages) ถือเป็นการจัดหมวดหมู่ข้อมูลเพื่อให้ผู้ใช้ค้นหาคำตอบได้ว่า "เพลงไหนทำถึงไหนแล้ว" ซึ่งต้องออกแบบให้เมนูและป้ายกำกับ (Label) สื่อสารได้ตรงกับความเข้าใจของทีมงาน [4], [5]
    *   (ก) ชื่อหนังสือ: Information Architecture
    *   (ข) เลขบท: Chapter 5
    *   (ค) เลขหน้า: **NO PAGE**

5.  **ระวังข้อมูลล้าสมัย (Outdated Content):** กระดานสถานะจะหมดความน่าเชื่อถือทันทีหากข้อมูลไม่อัปเดต เว็บไซต์ที่แสดงข้อมูลเก่าส่งผลเสียต่อการทำงานของทีมอย่างมาก ดังนั้นต้องมีระบบที่แน่ใจว่าสถานะเพลงจะถูกเปลี่ยนตามจริงเสมอ [6]

    *   (ก) ชื่อหนังสือ: Web Bloopers

8.  **ขั้นตอนการทำงานที่ยุ่งยาก (Agonizing Task Flow):** หากการย้ายสถานะเพลงเพลงหนึ่งต้องผ่านขั้นตอนที่ซับซ้อนเกินความจำเป็น จะทำให้ผู้ใช้รู้สึกหงุดหงิดและไม่ยากใช้งาน การออกแบบต้องลดภาระของผู้ใช้และทำให้การเปลี่ยนสถานะทำได้ง่ายที่สุด [10]
    *   (ก) ชื่อหนังสือ: Web Bloopers

1. **ห้ามใช้คำศัพท์เทคนิคคอมพิวเตอร์ (Geek Speak):** ผู้พัฒนามักเผลอใช้คำที่เป็นภาษาเฉพาะของโปรแกรมเมอร์ที่ผู้ใช้ทั่วไปไม่เข้าใจ เช่นคำว่า "field", "icon", หรือ "dialog" ซึ่งควรเปลี่ยนเป็นภาษาที่ผู้ใช้ทั่วไปใช้สื่อสารกันในชีวิตประจำวัน [1], [2]

## A
จากแหล่งข้อมูล **ARIA Authoring Practices Guide (APG)** [1-3] และข้อกำหนดที่เกี่ยวข้องในแหล่งข้อมูล WCAG 2.2 [4, 5] สรุปแบบแผน (Patterns) และข้อกำหนดทางเทคนิคได้ดังนี้ครับ (หมายเหตุ: รายละเอียดคุณสมบัติและปุ่มกดบางส่วนเป็นความรู้เพิ่มเติมจากแนวทางปฏิบัติของ APG นอกเหนือจากข้อความสั้นในแหล่งข้อมูล):

1. **กล่องยืนยันก่อนทำสิ่งที่ถอยไม่ได้ (Modal Dialog)**
   - **ชื่อแบบแผน:** **Dialog (Modal)** [2, 3]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/` [2]
   - **(ก) คุณสมบัติบังคับ:** ต้องใช้ `role="dialog"` และ `aria-modal="true"` พร้อมมี Accessible Name [ภายนอกแหล่งข้อมูล]
   - **(ข) แป้นพิมพ์:** ต้องกด `Escape` เพื่อปิด และ `Tab` เพื่อเลื่อนโฟกัสวนอยู่เฉพาะภายใน Dialog เท่านั้น [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** เมื่อเปิด ต้องย้ายโฟกัสเข้าไปยังองค์ประกอบแรกใน Dialog; เมื่อปิด ต้องย้ายโฟกัสกลับไปยังปุ่มที่เป็นจุดเริ่มต้น [สอดคล้องกับแนวทางใน 135]

2. **เมนูจุดสามจุดที่มุมขวา (Menu Button)**
   - **ชื่อแบบแผน:** **Menu Button** [2, 3, 6]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/` [2]
   - **(ก) คุณสมบัติบังคับ:** องค์ประกอบปุ่มต้องมี `aria-haspopup="true"` (หรือ `"menu"`) และ `aria-expanded` เพื่อบอกสถานะการเปิด-ปิด [ภายนอกแหล่งข้อมูล]
   - **(ข) แป้นพิมพ์:** `Enter`, `Space` หรือ `ArrowDown` เพื่อเปิดเมนู; `ArrowDown`/`ArrowUp` เพื่อเลือกรายการ [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** เมื่อเปิด โฟกัสต้องย้ายไปที่รายการเมนูแรก [ภายนอกแหล่งข้อมูล]

3. **ปุ่มสลับโหมด ตัวเลข/คอร์ด (Toggle Button)**
   - **ชื่อแบบแผน:** **Button (Toggle Button)** [2, 7]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/button/` [2]
   - **(ก) คุณสมบัติบังคับ:** ต้องมี `aria-pressed` เพื่อบอกว่าสถานะปัจจุบันถูกกด (โหมดหนึ่ง) หรือไม่กด (อีกโหมดหนึ่ง) [7]
   - **(ข) แป้นพิมพ์:** `Enter` หรือ `Space` เพื่อสลับสถานะ [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** โฟกัสยังคงอยู่ที่ตัวปุ่มเดิม [ภายนอกแหล่งข้อมูล]

4. **ช่องค้นหาเพลงที่มีรายการชื่อเพลงเด้งขึ้นมาให้เลือก (Combobox)**
   - **ชื่อแบบแผน:** **Combobox** [2, 3]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/combobox/` [2]
   - **(ก) คุณสมบัติบังคับ:** `role="combobox"`, `aria-autocomplete`, `aria-expanded` และ `aria-controls` เชื่อมไปยังรายการที่เด้งขึ้นมา [ภายนอกแหล่งข้อมูล]
   - **(ข) แป้นพิมพ์:** `ArrowDown` เพื่อเข้าสู่รายการตัวเลือก และ `Enter` เพื่อเลือกรายการ [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** โฟกัสหลักอยู่ที่ช่องป้อนข้อมูล แต่ใช้ `aria-activedescendant` เพื่อระบุรายการที่ถูกเลือกในปัจจุบัน [ภายนอกแหล่งข้อมูล]

5. **แถบบอกว่ากำลังบันทึก/บันทึกแล้ว (Status Message)**
   - **ชื่อแบบแผน:** **Alert** หรือ **Status** [4, 5]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/alert/` [2]
   - **(ก) คุณสมบัติบังคับ:** ต้องใช้ `role="status"` หรือ `role="alert"` เพื่อให้เทคโนโลยีสิ่งอำนวยความสะดวกแจ้งเตือนผู้ใช้โดยอัตโนมัติ [4, 5]
   - **(ข) แป้นพิมพ์:** โดยปกติไม่ต้องมีการโต้ตอบผ่านคีย์บอร์ด [4]
   - **(ค) จุดโฟกัส:** **ห้ามย้ายโฟกัส** ไปที่ข้อความนี้ (presented... without receiving focus) เพื่อไม่ให้ขัดจังหวะการทำงานของผู้ใช้ [4]

6. **แถบแท็บสลับระหว่างเนื้อร้องกับโน้ต (Tabs)**
   - **ชื่อแบบแผน:** **Tabs** [2, 8, 9]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/tabs/` [2]
   - **(ก) คุณสมบัติบังคับ:** ประกอบด้วย `role="tablist"`, `role="tab"` และ `role="tabpanel"` [8]
   - **(ข) แป้นพิมพ์:** `ArrowLeft`/`ArrowRight` เพื่อเลื่อนสลับระหว่างแท็บ [ภายนอกแหล่งข้อมูล]
   - (ค) **จุดโฟกัส:** โฟกัสย้ายไปตามแท็บที่ถูกเลือก และใช้ `Tab` เพื่อกระโดดเข้าสู่เนื้อหาใน `tabpanel` [สอดคล้องกับ 135]

7. **ปุ่มพับ/คลี่ท่อนเพลง (Disclosure)**
   - **ชื่อแบบแผน:** **Disclosure (Show/Hide)** [2, 5]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/` [2]
   - **(ก) คุณสมบัติบังคับ:** ปุ่มควบคุมต้องมี `aria-expanded` บอกสถานะ (true/false) และ `aria-controls` ระบุเนื้อหาที่ถูกคุม [5]
   - **(ข) แป้นพิมพ์:** `Enter` หรือ `Space` เพื่อพับหรือคลี่เนื้อหา [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** โฟกัสยังคงอยู่ที่ปุ่มเดิมเพื่อให้ผู้ใช้ทำงานต่อได้ [ภายนอกแหล่งข้อมูล]

8. **รายการเพลงที่ลากย้ายลำดับได้ (Reorderable List)**
   - **ชื่อแบบแผน:** **Listbox (Rearrangeable)** หรือแนวทาง **Drag-and-Drop** [2, 10, 11]
   - **ที่อยู่หน้าเว็บ:** `https://www.w3.org/WAI/ARIA/apg/practices/drag-and-drop/` [2]
   - **(ก) คุณสมบัติบังคับ:** ต้องมีกลไกทางเลือกที่ไม่ต้องใช้การลาก (Dragging) เช่น ปุ่มย้ายลำดับ [10] และแจ้งสถานะผ่าน aria-properties [12]
   - **(ข) แป้นพิมพ์:** ใช้ปุ่มลูกศรเพื่อเลือกรายการ และใช้ปุ่มคำสั่ง (เช่น `Space` หรือปุ่มลูกศรพร้อม Modifier) เพื่อย้ายลำดับ [ภายนอกแหล่งข้อมูล]
   - **(ค) จุดโฟกัส:** โฟกัสต้องติดตามรายการที่กำลังถูกย้าย หรือมีการแจ้งเตือนลำดับใหม่ผ่าน Live Region [ภายนอกแหล่งข้อมูล]

ผมได้ทำการค้นหาข้อมูลเพิ่มเติมจากแหล่งข้อมูลสาธารณะของ APG เพื่อให้ได้รายละเอียดทางเทคนิคที่ครบถ้วนที่สุดสำหรับแต่ละแบบแผน คุณสามารถตรวจสอบรายละเอียดเชิงลึกได้ในหน้าเว็บของแต่ละแบบแผนที่ระบุไว้ครับ หากต้องการให้สร้างสรุปเปรียบเทียบหรือแนวทางปฏิบัติเพิ่มเติมแจ้งได้เลยครับ

## A
วิธีทดสอบและเกณฑ์การตรวจให้ผ่านตามเอกสาร WCAG 2.2 และเอกสารประกอบ (Understanding) สำหรับข้อกำหนดทั้ง 8 ข้อ มีรายละเอียดดังนี้ครับ:

**1. 2.5.8 ขนาดเป้าหมายขั้นต่ำ (Target Size - Minimum)**
*   **เกณฑ์ตัวเลข:** เป้าหมายอินเทอร์เฟซ (Target) ต้องมีขนาดอย่างน้อย **24 x 24 CSS pixels** [ในแหล่ง] [1]
*   **วิธีทดสอบแบบ ใช่/ไม่ใช่:** หากขนาดเล็กกว่าเกณฑ์ ให้ใช้การวาดวงกลมเส้นผ่านศูนย์กลาง 24 CSS pixels วางทับที่จุดกึ่งกลางของเป้าหมายนั้น หากวงกลมของเป้าหมายที่เล็กกว่าเกณฑ์ไม่ไปซ้อนทับกับเป้าหมายอื่นหรือวงกลมของเป้าหมายอื่น ถือว่าผ่าน (Spacing Exception) [ในแหล่ง] [1]
*   **ข้อยกเว้น:** เป้าหมายที่เป็นลิงก์แทรกในประโยค (Inline), เป้าหมายที่ถูกควบคุมโดย User Agent (เบราว์เซอร์) โดยผู้สร้างไม่ได้ปรับแต่ง, หรือกรณีที่ขนาดเป้าหมายนั้นจำเป็นอย่างยิ่งต่อการสื่อความหมาย (Essential) [ในแหล่ง] [1]
*   **กรณีที่คนมักเข้าใจผิด:** หลายคนเข้าใจว่าทุกปุ่มต้องใหญ่กว่า 24px เสมอ แต่จริงๆ แล้วปุ่มเล็กกว่านั้นสามารถผ่านได้ถ้ามี **"ระยะห่าง"** รอบข้างที่กว้างพอตามวิธีทดสอบวงกลม [ในแหล่ง] [1]

**2. 2.4.11 โฟกัสไม่ถูกบัง (Focus Not Obscured - Minimum)**
*   **เกณฑ์ตัวเลข:** วัดแบบ ใช่/ไม่ใช่ — เมื่อส่วนประกอบรับ Focus (เช่น การ Tab) ส่วนประกอบนั้นต้อง **"ไม่ถูกบังจนมิด"** (Not entirely hidden) โดยเนื้อหาที่ผู้สร้างเว็บสร้างขึ้น (เช่น Sticky Header หรือ Popup) [ในแหล่ง] [2]
*   **วิธีทดสอบ:** ตรวจสอบว่ามีส่วนใดส่วนหนึ่งของกรอบโฟกัสหรือตัวส่วนประกอบเองโผล่พ้นเนื้อหาที่มาบังหรือไม่ [ภายนอกแหล่ง]
*   **ข้อยกเว้น:** หากเนื้อหาที่มาบังนั้นถูกเปิดขึ้นโดย **"ผู้ใช้"** เอง และผู้ใช้สามารถปิดหรือเลื่อนเนื้อหานั้นออกไปได้โดยไม่ต้องเลื่อนโฟกัสไปที่อื่น ถือว่าไม่ละเมิดข้อนี้ [ในแหล่ง] [3]
*   **กรณีที่คนมักเข้าใจผิด:** ข้อนี้ในระดับ AA อนุญาตให้ถูกบัง **"บางส่วน"** ได้ แต่ห้ามบัง **"ทั้งหมด"** (ถ้าจะห้ามบังเลยแม้แต่นิดเดียวต้องไปดูข้อ 2.4.12 ระดับ AAA) [ในแหล่ง] [2, 3]

**3. 2.4.13 หน้าตากรอบโฟกัส (Focus Appearance)**
*   **เกณฑ์ตัวเลข 1:** พื้นที่ของกรอบโฟกัส (Focus Indicator) ต้องมีขนาดอย่างน้อยเท่ากับ **เส้นรอบรูปที่มีความหนา 2 CSS pixels** ของส่วนประกอบนั้นขณะที่ยังไม่มีโฟกัส [ในแหล่ง] [4]
*   **เกณฑ์ตัวเลข 2:** ค่าความต่างสี (Contrast Ratio) ต้องมีอย่างน้อย **3:1** ระหว่างพิกเซลของกรอบโฟกัสเทียบกับสีเดิมก่อนมีโฟกัส [ในแหล่ง] [4]
*   **ข้อยกเว้น:** กรอบโฟกัสที่กำหนดโดยเบราว์เซอร์เอง (User Agent) และผู้สร้างไม่ได้ไปแก้ไขสีหรือหน้าตา [ในแหล่ง] [4]
*   **กรณีที่คนมักเข้าใจผิด:** การคำนวณพื้นที่เส้นรอบรูปจะไม่นับรวมเอฟเฟกต์ Shadow หรือ Glow ที่ฟุ้งออกมานอกขอบเขตของส่วนประกอบ [ในแหล่ง] [5]

**4. 3.3.8 การเข้าสู่ระบบที่ไม่ใช้ความจำ (Accessible Authentication - Minimum)**
*   **วิธีทดสอบแบบ ใช่/ไม่ใช่:** กระบวนการยืนยันตัวตนต้อง **"ไม่มีขั้นตอนใดที่บังคับให้ผู้ใช้ต้องทำแบบทดสอบทางปัญญา"** (Cognitive function test) เช่น การจำรหัสผ่าน, การแก้โจทย์เลข, หรือการถอดรหัสภาพ [ในแหล่ง] [6, 7]
*   **ข้อยกเว้น (ผ่านได้ถ้ามี):** มีวิธีล็อกอินสำรองที่ไม่ต้องใช้ความจำ, หรือเว็บสนับสนุนระบบ **Copy & Paste** รหัสผ่าน, หรือรองรับการทำงานของ **Password Manager** [ในแหล่ง] [6, 8]
*   **กรณีที่คนมักเข้าใจผิด:** การกรอกชื่อผู้ใช้, อีเมล หรือเบอร์โทรศัพท์ **"ไม่ถือเป็น"** แบบทดสอบทางปัญญา เพราะเป็นข้อมูลส่วนตัวพื้นฐานที่ผู้ใช้ใช้เป็นประจำ [ในแหล่ง] [7]

**5. 3.2.6 ตัวช่วยอยู่ที่เดิม (Consistent Help)**
*   **วิธีทดสอบแบบ ใช่/ไม่ใช่:** หากหน้าเว็บมีกลไกช่วยเหลือ (เช่น ข้อมูลติดต่อมนุษย์, แชทบอท, FAQ) และกลไกเหล่านั้นปรากฏซ้ำในหลายหน้า จะต้องวางอยู่ใน **"ลำดับสัมพันธ์เดิม"** (Same relative order) เสมอ [ในแหล่ง] [9]
*   **เกณฑ์ตัวเลข:** ตรวจสอบลำดับจากการ Serialize (ลำดับใน Code) ว่ายังคงเดิมหรือไม่ [ในแหล่ง] [10]
*   **กรณีที่คนมักเข้าใจผิด:** ไม่ได้บังคับว่า "ตำแหน่งภาพ" (Visual position) ต้องเป๊ะเท่ากันทุกพิกเซล แต่ลำดับเมื่อไล่ดูตามเนื้อหาต้องเหมือนเดิม และอนุญาตให้เปลี่ยนได้หาก **"ผู้ใช้"** เป็นคนสั่งเปลี่ยนเอง (เช่น เปลี่ยนการแสดงผล) [ในแหล่ง] [9, 10]

**6. 3.3.7 ไม่ต้องกรอกซ้ำ (Redundant Entry)**
*   **วิธีทดสอบแบบ ใช่/ไม่ใช่:** ข้อมูลที่ผู้ใช้เคยกรอกไปแล้วในขั้นตอนก่อนหน้าของกระบวนการเดียวกัน (Same process) จะต้อง **"ถูกเติมให้อัตโนมัติ"** (Auto-populated) หรือ **"มีให้เลือก"** โดยไม่ต้องพิมพ์ใหม่ [ในแหล่ง] [11]
*   **ข้อยกเว้น:** เมื่อความปลอดภัยบังคับ (เช่น ยืนยันรหัสผ่านใหม่), ข้อมูลเดิมใช้ไม่ได้แล้ว, หรือข้อมูลนั้นจำเป็นต้องพิมพ์ใหม่เพื่อยืนยันความถูกต้อง (Essential) [ในแหล่ง] [11]
*   **กรณีที่คนมักเข้าใจผิด:** ข้อนี้ใช้กับข้อมูลใน **"กระบวนการเดียวกัน"** เท่านั้น หากเป็นคนละธุรกรรมไม่บังคับ (แต่อาจเป็นเทคนิคเสริม) [ในแหล่ง] [11]

**7. 1.4.12 ระยะห่างข้อความ (Text Spacing)**
*   **เกณฑ์ตัวเลข:** เมื่อผู้ใช้ปรับแต่งระยะห่าง (Style override) ดังนี้ เนื้อหาต้องไม่สูญเสียการใช้งาน:
    *   Line height $\ge$ 1.5 เท่าของขนาดตัวอักษร [ในแหล่ง] [12]
    *   Spacing following paragraphs $\ge$ 2 เท่าของขนาดตัวอักษร [ในแหล่ง] [12]
    *   Letter spacing $\ge$ 0.12 เท่าของขนาดตัวอักษร [ในแหล่ง] [12]
    *   Word spacing $\ge$ 0.16 เท่าของขนาดตัวอักษร [ในแหล่ง] [12]
*   **กรณีที่คนมักเข้าใจผิด:** เว็บ **"ไม่จำเป็น"** ต้องตั้งค่าเริ่มต้นด้วยตัวเลขเหล่านี้ แต่ต้องออกแบบมาให้ **"รองรับ"** หากผู้ใช้สั่งปรับผ่าน Browser Extension แล้วตัวอักษรต้องไม่ซ้อนทับกันหรือล้นจนกดปุ่มไม่ได้ [ในแหล่ง] [13]

**8. 1.4.10 การจัดใหม่ให้พอจอแคบ (Reflow)**
*   **เกณฑ์ตัวเลข:** เนื้อหาต้องแสดงผลได้โดย **"ไม่ต้องเลื่อนหน้าจอสองทิศทาง"** (ห้ามมี Scroll bar แนวนอนและแนวตั้งพร้อมกัน) เมื่อดูที่ความกว้างเทียบเท่า **320 CSS pixels** [ในแหล่ง] [14, 15]
*   **วิธีทดสอบ:** เปิดเว็บหน้าจอปกติ (1280px) แล้วทำการ Zoom ไปที่ **400%** แล้วตรวจสอบว่าเนื้อหาไหลลงมาในแนวตั้งทั้งหมดหรือไม่ [ในแหล่ง] [15]
*   **ข้อยกเว้น:** เนื้อหาที่จำเป็นต้องเห็นภาพรวมสองมิติ เช่น แผนที่, ตารางข้อมูลขนาดใหญ่ (Data Table), วิดีโอ, หรือเกม [ในแหล่ง] [16]

จากการเจาะลึกหนังสือ **Information Architecture for the World Wide Web (Morville & Rosenfeld, 2006)** ในบทที่กำหนด (1, 2, 3, 8, 10, 12 และ 13-21) เพื่อประยุกต์ใช้กับเว็บคลังเพลงนมัสการสำหรับผู้สูงอายุและทีมอาสาสมัคร มีหลักการที่สามารถแปลงเป็นข้อบังคับที่ตรวจวัดได้ดังนี้ครับ:

1. **บทที่ 3 หัวข้อย่อย 3.2. Information Needs**
   *   **ข้อบังคับ:** ระบบค้นหาและระบบนำทางต้องให้ความสำคัญสูงสุดกับการรองรับพฤติกรรม **"Known-item seeking"** (การค้นหาของที่รู้อยู่แล้วว่ามี) เพื่อให้ผู้สูงอายุที่จำชื่อเพลงได้สามารถเข้าถึงเนื้อเพลงที่ต้องการได้ทันทีโดยตรง [ในแหล่ง] [1, 2]

2. **บทที่ 8 หัวข้อย่อย 8.7.1. Which Content Components to Display**
   *   **ข้อบังคับ:** ในหน้าแสดงผลการค้นหา ต้องแสดงส่วนประกอบเนื้อหา (Content Components) ที่ช่วยในการแยกแยะเพลงที่มีชื่อคล้ายกันได้ทันที (เช่น ชื่อเพลง, หมวดหมู่เทศกาล, หรือบรรทัดแรกของเนื้อเพลง) เพื่อลดภาระการคลิกเข้าไปดูข้างในโดยไม่จำเป็นสำหรับผู้สูงอายุ [ในแหล่ง] [3, 4]

3. **บทที่ 8 หัวข้อย่อย 8.8.3.1. Repeat search in results page**
   *   **ข้อบังคับ:** หน้าแสดงผลการค้นหาต้องแสดงคำที่ผู้ใช้พิมพ์ค้นหาค้างไว้ในช่อง Search Box เสมอ เพื่อให้ผู้ใช้ (โดยเฉพาะผู้สูงอายุที่อาจลืมสิ่งที่พิมพ์ไปแล้ว) สามารถตรวจสอบและแก้ไขคำค้นหาเพื่อเริ่มค้นหาใหม่ได้สะดวก [ในแหล่ง] [5]

4. **บทที่ 10 หัวข้อย่อย 10.5.2. Search-Log Analysis**
   *   **ข้อบังคับ:** ทีมอาสาสมัครต้องมีการตรวจสอบ **"Search Logs"** (บันทึกคำค้นหา) เป็นประจำ เพื่อดูว่าคำค้นหาใดที่ผู้สูงอายุใช้บ่อยแต่หาไม่เจอ (เช่น การสะกดผิด หรือการใช้ชื่อเทศกาลที่ต่างออกไป) และนำมาปรับปรุงดัชนีหรือคำศัพท์ควบคุมในระบบ [ในแหล่ง] [6]

5. **บทที่ 12 หัวข้อย่อย 12.9. Putting It All Together: Information Architecture Style Guides**
   *   **ข้อบังคับ:** ต้องจัดทำ **"IA Style Guide"** ที่ระบุมาตรฐานการตั้งชื่อเพลง การจัดหมวดหมู่ และการใส่ Metadata เพื่อให้อาสาสมัครทั้ง 3-5 คนทำงานไปในทิศทางเดียวกัน และป้องกันภาวะ "สถาปัตยกรรมคลาดเคลื่อน" (Architectural Drift) เมื่อมีการเพิ่มเพลงใหม่ในอนาคต [ในแหล่ง] [7, 8]

6. **บทที่ 14 หัวข้อย่อย 14.1.5. Physical Access**
   *   **ข้อบังคับ:** การออกแบบเว็บต้องคำนึงถึง **"Universal Usability"** โดยเน้นความชัดเจนของการอ่าน (Legibility) เช่น การใช้ตัวอักษรขนาดใหญ่และสีที่ตัดกัน เพื่อรองรับข้อจำกัดทางกายภาพของผู้สูงอายุที่เข้ามาใช้งานในโบสถ์ [ในแหล่ง] [9, 10]

7. **บทที่ 19 หัวข้อย่อย 19.3.2. Guides**
   *   **ข้อบังคับ:** เว็บควรมีหน้า **"Guides"** ที่รวบรวมเพลงตามความต้องการเฉพาะหน้า เช่น "เพลงสำหรับเทศกาลอีสเตอร์" หรือ "เพลงสำหรับพิธีมหาสนิท" ซึ่งเป็นการจัดกลุ่มหน้าเดียวที่ช่วยให้ผู้สูงอายุหาเพลงตามเทศกาลได้ง่ายกว่าการไล่หาจากหมวดหมู่ใหญ่ [ในแหล่ง] [11]

    * ให้ใส่เลขห้องไว้ที่**จุดเริ่มต้นของทุกบรรทัด (System)** โดยตำแหน่งที่เหมาะสมคือวางไว้เหนือ clef (หรือเหนือตำแหน่งเริ่มต้นบรรทัด) [11] และสำหรับงานที่เป็นเพลงร้องที่ทุกคนใช้แผ่นเดียวกัน Gould ระบุว่าใช้เพียงเลขห้องกำกับก็เพียงพอ ไม่จำเป็นต้องใส่ตัวอักษรกำกับตอน (rehearsal marks) เพิ่มเติม [12]

7. **ระบบโน้ตตัวเลข (Jianpu)**
    * (ก) [ไม่มีในแหล่ง]

## A
จากการตรวจสอบแหล่งข้อมูล SMuFL (smufl-01 ถึง smufl-05 และ smufl-metadata) มีข้อมูลสรุปตามเงื่อนไขที่คุณกำหนดดังนี้ครับ:

1.  **หน่วยวัดหลักและความสัมพันธ์กับ em:** SMuFL กำหนดให้ **staff spaces** (หรือ "spaces") เป็นหน่วยวัดหลักในการระบุตำแหน่งและขนาดของสัญลักษณ์ [ในแหล่ง] โดยความสัมพันธ์พื้นฐานสำหรับซอฟต์แวร์จัดพิมพ์จำหน่าย (scoring applications) คือ **1 staff space = 0.25 em** (หรือ 4 staff spaces เท่ากับ 1 em) เพื่อให้สอดคล้องกับบรรทัด 5 เส้นมาตรฐาน [smufl-01: scoring metrics glyph registration, 673, 691]
2.  **ความสัมพันธ์ em สำหรับงานเอกสาร:** หากใช้ในบริบทของงานพิมพ์ข้อความ (text-based applications) SMuFL แนะนำให้ใช้สัดส่วน **1 staff space = 0.2 em** เพื่อให้ความสูงของบรรทัด (line spacing) สอดคล้องกับฟอนต์ข้อความทั่วไป [ในแหล่ง] [smufl-01: text metrics glyph registration, 695]
3.  **ค่าเริ่มต้นใน engravingDefaults สำหรับเส้นแบ่งห้อง:** มีการกำหนดค่าความหนาและระยะห่างที่ใช้กับเส้นแบ่งห้องและเส้นย้อน [ในแหล่ง] ดังนี้:
    *   เส้นแบ่งห้องเดี่ยว: `thinBarlineThickness` (ค่าแนะนำ 0.16)
    *   เส้นแบ่งห้องคู่/เส้นจบ: `thickBarlineThickness` (ค่าแนะนำ 0.5) และ `barlineSeparation` (ระยะห่างระหว่างเส้น 0.4)
    *   เส้นย้อน: `repeatBarlineDotSeparation` (ระยะห่างของจุดจากเส้น 0.16) [smufl-01: engravingdefaults, 690-691]
4.  **ค่าเริ่มต้นใน engravingDefaults สำหรับเส้นโค้งและขีดยาว:** มีค่าที่ใช้กำหนดลักษณะทางกายภาพของเส้นเชื่อมเสียงและเส้นบอกช่วงเสียง [ในแหล่ง] ดังนี้:
    *   เส้นโค้งเชื่อมเสียง (slur): `slurMidpointThickness` (ความหนากลางเส้น 0.22) และ `slurEndpointThickness` (ความหนาปลายเส้น 0.1)
    *   เส้นโค้งเชื่อมเสียง (tie): `tieMidpointThickness` (0.2) และ `tieEndpointThickness` (0.1)
    *   เส้นบอกช่วงเสียง/ขีดยาว: `octaveLineThickness` (0.11) และ `lyricLineThickness` (0.12 - อาจประยุกต์ใช้กับขีดลากเสียงได้) [smufl-01: engravingdefaults, 690-691]
5.  **รายการที่ไม่มีใน engravingDefaults:** สำหรับเครื่องหมายย้อน (**segno/coda**) และเครื่องหมายค้างเสียง (**fermata**) **ไม่มี** การกำหนดค่าความหนาหรือระยะห่างในส่วน `engravingDefaults` [ในแหล่ง] เนื่องจากสัญลักษณ์เหล่านี้ถูกกำหนดเป็น "Glyphs" (ตัวอักษร) ที่มีความกว้างและรูปร่างตายตัวในฟอนต์อยู่แล้ว ไม่ได้วาดขึ้นจากเส้นพื้นฐานในส่วน defaults [smufl-01: engravingdefaults, 690]
6.  **การอิงขนาดสัญลักษณ์ให้สัมพันธ์กับตัวเลข:** การกำหนดขนาดต้องอิงกับหน่วย **staff spaces** เป็นหลัก [ในแหล่ง] แม้แผ่นเพลงเจียนพู่จะไม่มีบรรทัด 5 เส้น แต่ SMuFL ระบุว่า **ตัวเลข** (ในที่นี้คือตัวเลขบอกจังหวะหรือตัวโน้ตเลข) ควรมีความสูงเท่ากับ **2 staff spaces** (หรือ 0.5 em) เพื่อให้สัดส่วนของสัญลักษณ์อื่นๆ (เช่น fermata หรือ segno) ที่ถูกออกแบบมาให้สัมพันธ์กับหน่วย space นี้ มีขนาดที่ถูกต้องและสมดุลเมื่อวางร่วมกับตัวเลข [smufl-01: scoring metrics glyph registration, 691-692]
