## Q
บริบท: เว็บคลังเพลงนมัสการไทย (Vue3 + Supabase). ปัญหาจริง: เพลงเดียวกันถูกใส่ซ้ำหลายใบ เข้าได้ 3 ทาง (พิมพ์ใหม่ · เปลี่ยนชื่อไปชนของเดิม · นำเข้าเป็นชุดจากหนังสือที่แปลงด้วย AI). ตาราง songs มีคอลัมน์ category = "เล่ม" (lem-yai/anuchon/dek-lek, เพิ่มเล่มใหม่ได้) และ book_refs = แท็กอ้างอิงหนังสือกระดาษ (คนละเรื่อง).

กติกาที่เจ้าของสั่ง: ชื่อเหมือนเป๊ะ+เล่มเดียวกัน = บล็อกไม่ให้บันทึก (approver ยืนยันข้ามได้) · ชื่อคล้าย = เตือนแต่ผ่านได้ · ชื่อเหมือนคนละเล่ม = ผ่านปกติ.

สิ่งที่ผมทำ (ขอให้คุณ "หาช่องโหว่" แบบ adversarial ไม่ต้องชม):
1) key เข้ม (ใช้บล็อก) = NFC → ลบ zero-width → แปลง U+0E4D+U+0E32 เป็น ำ → ตัดเลขนำหน้าชื่อ (ทั้งเลขอารบิกและไทย) → ลบช่องว่างทั้งหมด → lowercase. **เก็บวรรณยุกต์/สระไว้ทั้งหมด**
2) key หลวม (ใช้เตือน) = key เข้ม → ลบเครื่องหมายวรรคตอน → ลบวรรณยุกต์+ไม้ไต่คู้+ทัณฑฆาต (U+0E47-U+0E4E) → ยุบสระเสียงยาว/สั้นคู่ ี→ิ ู→ุ ื→ึ → ยุบอักษรซ้ำติดกัน; แล้วถือว่า "คล้าย" ถ้า key หลวมเท่ากัน หรือ edit distance ≤1 (เฉพาะเมื่อยาว ≥4)
3) เทียบรายเล่มจาก category; เพลงที่ category เป็น null จัดเป็นถังของตัวเอง ไม่เทียบกับเพลงที่มีเล่ม
4) บล็อกที่จุดเขียนลง songs (publish/approve) + เตือนสดขณะพิมพ์ + unique index ระดับ DB (coalesce(category,'__none__'), song_title_key(title_th)) สำหรับกันการนำเข้าเป็นชุดที่ไม่ผ่านเว็บ

คำถาม (ตอบสั้น เป็นข้อ ๆ):
A. การลบช่องว่างทั้งหมดใน key เข้ม จะทำให้ "คนละเพลง" ชนกันผิดๆ ในภาษาไทยได้ไหม ยกตัวอย่างจริง
B. การยุบสระ ี→ิ / ู→ุ / ื→ึ ในชั้น "เตือน" จะเตือนพร่ำเพรื่อจนคนกดข้ามทุกครั้งไหม
C. ช่องโหว่ที่ยังกันไม่ได้ — เช่น ชื่อเดียวกันแต่สะกดคนละแบบสิ้นเชิง, ชื่อภาษาอังกฤษ, เพลงเดียวกันคนละชื่อ, ตัวเลขเพลงซ้ำ — อันไหนสำคัญสุดที่ควรทำต่อ

## A
นี่คือการวิเคราะห์หาช่องโหว่ (Adversarial Review) ตามข้อๆ ครับ:

A. การลบช่องว่างทั้งหมดใน Key เข้ม

เกิดการชนผิดได้จริง (False Positive) ในภาษาไทย การลบช่องว่างเปลี่ยนโครงสร้างและความหมายของประโยคได้ เช่น

"รักแท้" vs "รัก แท้" (คำเดียวกัน - โอเค)

"ตา กลม" (ตา-กลม) vs "ตาก ลม" (ตาก-ลม) → พอตัด space เหลือ ตากลม ชนกันเป๊ะ ทั้งที่เป็นคนละบริบท/คนละเพลง

"พรอันยิ่งใหญ่" vs "พร อัน ยิ่งใหญ่" → พรอันยิ่งใหญ่ ชนกับ "พร อันยิ่งใหญ่" (ถ้าตัดคำผิด)

B. การยุบสระ (ี$\rightarrowิ,ู\rightarrowุ,ื\rightarrow$ึ) ใน Key หลวม

เตือนพร่ำเพรื่อแน่นอน (Noise High) คำไทยเปลี่ยนสระเปลี่ยนความหมายทันที คนละเพลงกันเลย เช่น

"สิบ" (10) vs "สืบ" (ค้นหา)

"สุข" (ความสุข) vs "สูง" (ความสูง - ถ้ามีส่วนประกอบอื่น) หรือ "จุด" vs "จูด"

ผลคือเวลานำเข้าเพลงใหม่จะเจอเตือนเตือนตลอดเวลา (False Alarm) จน Approver เกิด Alert Fatigue และติดนิสัยกด "ข้าม/ยืนยัน" โดยไม่ดูเนื้อหา

C. ช่องโหว่ที่ยังกันไม่ได้ — อันไหนสำคัญสุด

"เพลงเดียวกันแต่คนละชื่อ" (Alternate Titles) สำคัญที่สุด

คลังเพลงนมัสการไทยมีปัญหานี้หนักที่สุด เช่น "พระเจ้าทรงเลี้ยงดู" vs "พระเจ้าทรงเป็นผู้เลี้ยง" (เพลงเดียวกัน Translate ต่างค่าย) หรือ "ทรงเป็นแผ่นดิน" vs "ข้าขอสโมสร"

การใช้แค่ title Match จะเอาไม่อยู่เลย เพลงซ้ำจะหลุดเข้าคลังเยอะมาก

สิ่งที่ควรทำต่อ: เปรียบเทียบ "ท่อนฮุก" (Chorus) หรือ "3 บรรทัดแรกของเนื้อร้อง" โดยใช้ Algorithm ในข้อ 2 มาจับเนื้อร้องด้วย ไม่ใช่จับแค่ชื่อเพลง

D. Unique Index ทำให้ Approver Override พังหรือไม่

พังแน่นอน ถ้าทำ Unique Index ที่ DB แล้ว UI จะกด Approve ข้ามไม่ได้ เพราะ Postgres จะ Reject ด้วย violates unique constraint ทันที

ทางออกที่ถูกต้อง:

อย่าใส่ Unique Index ที่ตารางหลัก (songs) หากต้องการให้มี Human Override

ใช้การแยก Flag: เพิ่มคอลัมน์ is_force_approved boolean DEFAULT false หรือ duplicate_override_reason

ถ้าต้องกัน Batch Import ระดับ DB จริงๆ: ให้สร้าง Partial Unique Index แทน

SQL
CREATE UNIQUE INDEX idx_prevent_dup_title 
ON songs (COALESCE(category, '__none__'), song_title_key(title_th)) 
WHERE (is_force_approved IS FALSE);


เวลา Batch Import ห้ามใส่ flag นี้เข้ามา (จะติด Index)
เวลา Approver จะข้าม ให้สั่ง UPDATE ตั้งค่า is_force_approved = true ตัว Index จะข้าม record นี้ทันที

E. กับดัก normalize NFC + Regexp ใน Postgres Immutable Function

Postgres ไม่ได้บิวต์อิน Unicode Normalization (NFC) ในตัวแบบง่ายๆ ก่อน Postgres 14 (ถ้าใช้ version เก่าต้องติดตั้ง extension unaccent หรือเรียก PL/Python/PL/v8)

IMMUTABLE จะพังถ้า Locale/Collation เปลี่ยน การใช้ Regexp กับภาษาไทยใน Function ที่ประกาศเป็น IMMUTABLE หาก DB ถูก dump/restore ไปเครื่องที่ Collation ต่างกัน ผลลัพธ์ Index อาจเพี้ยนได้

เรื่องสระ ำ (U+0E32 + U+0E4D): การลบวรรณยุกต์ออกด้วย Regexp Range เช่น [U+0E47-U+0E4E] อาจไปโดนลบ นิคหิต (U+0E4D) ก่อนที่จะแปลงเป็น สระ ำ ทำให้สระ ำ เพี้ยนกลายเป็น สระ อา (U+0E32) ได้ ต้องเรียง Order การเปลี่ยนสตริงให้ดีมากๆ
